## 3. 待处理问题

### 3.1 切片 3 正确性

1. **空作品可能被误判为成功。** 空 Alda 可以解析为 0 声部、0 时长；未指定时长和乐器约束时，
   校验结果是“语法通过、时长未检查、乐器未检查”。`Agent` 当前以“没有 `Fail`”作为成功条件，
   因而可能保存空作品。需要新增明确的非空、非零声部和非零事件检查。
2. **截断状态跨修正轮残留。** `was_truncated` 在循环外初始化，某一轮被设为 `true` 后不会在下一轮
   重置；后续即使生成完整作品也会继续被判失败。截断状态应按轮计算，最终结果只反映相应候选。
3. **失败退出码误报。** `create` 达到修正上限后打印失败但仍返回成功退出码，不适合作为自动化门禁。
4. 缺少创作成功、三轮修正、显式继续、失败保护、完整曲目和即兴片段的纵向自动化测试。

### 3.2 Alda 运行与进程控制

1. `AldaRunner.timeout` 尚未使用；命令通过阻塞的 `output()`/`status()` 执行，没有实际超时、取消或
   子进程终止机制。
2. MIDI 集成测试被忽略；本次真实 smoke 中 MIDI 导出失败。
3. `alda-smoke` 没有调用 `play()`/`stop()`，因此不能证明播放、停止或无残留进程。
4. 输出大小只在子进程退出后检查 stdout，不能限制运行中的输出，也未限制 stderr。
5. 默认测试直接依赖本机 Alda；缺少 Alda 时会失败，不符合默认测试离线的原计划。

### 3.3 DeepSeek 与证据链

1. 仓库中的 SSE fixture 没有被生产解析路径直接使用；现有测试主要重复了局部解析逻辑。
2. 没有 HTTP mock 覆盖请求字段、401、429、400、网络失败和真实流读取路径。
3. 没有 `Ctrl+C` 或其他显式取消实现与测试。
4. 仓库内没有真实 DeepSeek smoke、长输出实验、完整创作、播放、人工试听或 secret scan 记录。

### 3.4 切片 4 计划问题

1. 计划中的新版本号使用 `current_version + 1`，而恢复操作会把 `current_version` 回退。恢复版本 1
   后继续修改会覆盖已有版本 2。新版本号应使用历史最大版本号加一，当前选中版本与下一版本号应
   分开表达。
2. 切片 4 设计把 `/reload` 延后，但首期需求和初始计划要求支持人工编辑后的显式重新读取、校验和
   采用。实施前需要统一范围，不能在完成验收时静默缺失。
3. 实施计划的 27 个步骤全部未勾选，底部自审清单却使用了“✅”表示规格映射，容易被误读为实现
   完成。自审标记应区分“计划已覆盖”和“实现已完成”。

### 3.5 文档和仓库状态

1. 初始实施计划总状态仍为“待执行”，没有按每个切片回填实际验证命令、偏差和证据。
2. 最新提交标题是文档移动，但同时把默认模型从 `deepseek-chat` 改为 `deepseek-v4-flash`，且没有
   对新默认值的真实 API 验证记录。
3. `.env.example`、需求文档和实现支持的键不一致，需要统一配置契约。

## 4. 模型名称配置期望

### 4.1 当前事实

`Config` 已能读取 `ALDA_AGENT_MODEL` 或 `model`，但源码仍把 `deepseek-v4-flash` 作为默认值；
`.env.example` 则写着 `deepseek-chat`。这既是硬编码，也会让示例、测试和实际运行选择不一致。

### 4.2 期望的不变量

1. **模型名称由运行配置显式指定，不在源码中硬编码具体模型名称。**
2. `.env` 至少明确提供 API key、base URL 和 model；缺少或为空的 model 应在发送请求前返回可操作
   的配置错误。
3. 配置值应原样传给 OpenAI-compatible 请求，不由客户端静默替换或猜测 Provider 默认模型。
4. `doctor` 和 smoke 应显示最终生效的 base URL 与模型名称，但不得显示 API key。
5. 自动化测试使用 `example-model` 等占位值验证配置传递，不断言任何真实模型名称。
6. `.env.example`、需求文档、实施计划和实现必须使用同一组键名；可以兼容旧别名，但应指定一个
   规范写法。

### 4.3 验收条件

- 修改 `.env` 中的 model 后，不重新编译即可切换请求模型。
- 缺少 model 时命令明确失败，不发起网络请求。
- 请求 fixture 或 mock 能证明配置的模型名称被写入请求体。
- `rg` 检查源码和测试时，不存在 Provider 的具体模型名称作为默认值或测试期望值；示例文档可以
  使用明确标注的占位符。

该要求只消除模型名称硬编码，不意味着现在需要抽象通用 Provider trait。

## 5. `simple-workflow` 使用反思

### 5.1 本次进度调研是否滥用

是，按任务规模看属于**过度触发**。最初请求只是只读的项目进度调研，一个主 agent 可以通过仓库
状态、计划文档、源码和验证命令完成。它没有多个独立交付物，也没有必须隔离上下文的长时间实现。

Brain、两个 Worker 和 Reviewer 的交叉检查确实发现了空作品误判、截断状态残留和切片 4 版本号
问题，独立复核有实际收益；但这些收益不能证明多 agent 应成为普通进度调研的默认路径。相同结果
可以由主 agent 先检查，再仅在发现高风险或证据冲突时按需增加一个 Reviewer。默认完整编排带来了
额外延迟、重复命令、上下文和协调成本，与项目“简单，直到不能更简单”的原则相冲突。

### 5.2 skill 本身的问题

`simple-workflow` 的核心原则没有明显问题。它明确要求：

- 先判断拆分是否有帮助；
- 一个 agent 能做好时不要拆分；
- 使用最少的 agent、任务和协调步骤；
- 只在真正独立时并行。

需要改进的是触发和退出语义：可以更明确写出“invoke skill 不等于必须 spawn sub-agent；若第一步
判断无需拆分，Master 直接完成任务即视为正确使用”。这样能避免调用者把 Brain → Worker → Review
误解成每次触发后的无条件流程。

### 5.3 `AGENTS.md` 调整结论

需要调整。原规则把“任务可以自然分解为并行或阶段性工作”作为强制触发条件，几乎覆盖所有非平凡
任务；又把 Brain → Workers → Review 写成无条件强制流程，直接覆盖了 skill 自身“一个 agent 能
做好就不要拆分”的成本判断。

“修改至少两个源文件”也不是可靠的复杂度指标：两个文件的机械修改可能非常简单，一个文件的协议、
并发或安全修改反而可能需要独立评审。只读调研、状态报告和文档编辑通常也不应默认多 agent。

最终决定从 `AGENTS.md` 删除整段强制使用规则，不在项目规则和 skill 元数据之间维护两套触发条件。
适用场景、负面触发条件和“invoke 不等于 spawn”统一由 `simple-workflow` 自身定义。
