# CLI 交互体验改进

> 来源：首期真实创作与完整试听验收
>
> 状态：首轮实施完成，真实终端反馈持续修正
>
> 方案：[CLI 交互体验改进方案](../iter/cli-ergonomics/README.md)
>
> 相关调研：[Coding Agent 的终端信息分层](../research/coding-agent-terminal-information-layout.md)

## 用户反馈

首期功能闭环可以完成真实创作，但当前 CLI 交互过于简陋，不符合人体工程学。该反馈是首期验收的
主要产品结论，也是下一阶段的核心需求。

## 当前事实

首轮改造已引入 reedline 多行编辑、历史、Tab 补全、分组命令、持久阶段行、活动 spinner、项目内模型
配置和本地能力降级。多行粘贴已显式启用 bracketed paste，不再按换行触发多次请求。

真实长会话仍暴露一项主要问题：会话历史、输入入口、活动/播放状态和项目摘要都落在同一滚动平面，且
项目摘要在每次提示符前重复。当前版本和实际播放版本虽语义正确，但连续出现时仍难以快速分辨。

## 需求边界

下一迭代需要在保留原生终端滚动记录和 reedline 的前提下形成清晰的信息层级。优先覆盖：

- 项目摘要只在启动或事实变化后显示，不因空输入重复；
- 输入块具有稳定边界，与上方会话历史明确分离；
- 活动状态保持临时，完成结果进入历史，二者不重复表达；
- 当前版本与实际播放版本明确区分；
- 完整项目事实继续由 `/project` 按需展开，常驻上下文保持单行低密度。

暂不引入全屏 TUI。只有出现固定底部输入、运行中排队消息或交互式历史浏览的真实需求时，才评估
ratatui 和 alternate screen。

项目尚未发布，不需要兼容现有 REPL 命令。若破坏性修改或重构能显著简化交互、澄清职责边界，可以
直接替换旧接口，不保留兼容别名或弃用周期。命令设计至少应明确区分：

- Agent 操作：自然语言创作、修改、澄清和继续修正；
- Alda 工具操作：校验、播放、停止和导出，不访问模型、不修改项目版本；
- 项目操作：状态、版本切换、采用外部乐谱和持久化设置。

目前不预设必须采用全屏 TUI、特定终端框架或 GUI。应先把真实使用中的关键摩擦转化为少量交互场景，
再选择能满足场景的最简单实现。

界面信息至少应形成两个可独立使用的视图：

- 项目视图：展示项目事实、当前版本、版本历史、约束和本地工具能力；
- 对话视图：展示用户与 Agent 的对话、澄清状态、生成阶段和 Agent 内部工具过程。

CLI 可以把项目摘要嵌入对话提示符，但不能把两个视图及其领域逻辑继续耦合在 REPL 实现中。方案应提供
不依赖终端控件的应用动作和只读视图数据，使后续 GUI 能直接复用，而不是重新实现项目或 Agent 流程。

首版一个 Project 对应一条持久对话。创建项目只建立作品上下文，不进入独立的素材录入向导，也不发起
模型请求；第一条自然语言消息成为对话首条消息和首次创作请求。打开已有项目时恢复这条对话。暂不增加
一个项目内的多会话选择和管理。

## 完成判定

下一轮至少用五次连续修改的真实会话验收：每条用户要求及对应版本结果易于定位；空输入不重复摘要；
当前版本、播放版本和活动阶段不会混淆；窄终端优先省略次要帮助，不截断输入和主要状态。
