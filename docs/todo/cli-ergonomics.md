# CLI 交互体验改进

> 来源：首期真实创作与完整试听验收
>
> 状态：需求已确认，方案待评审
>
> 方案：[CLI 交互体验改进方案](../iter/cli-ergonomics/README.md)

## 用户反馈

首期功能闭环可以完成真实创作，但当前 CLI 交互过于简陋，不符合人体工程学。该反馈是首期验收的
主要产品结论，也是下一阶段的核心需求。

## 当前事实

当前 REPL 基于标准输入输出的逐行循环：

- 始终使用单一的 `> ` 提示符，项目、生成、校验和播放状态缺少持续可见的层次；
- 模型流式文本、系统提示、检查结果和错误共享同一终端输出，长任务中不易定位当前阶段；
- 没有行编辑、历史导航、命令补全或命令提示；
- 新项目用单独一行 `.` 结束多行素材输入，依赖用户记忆约定；
- 功能主要通过斜杠命令暴露，`/help` 是静态命令清单，缺少上下文提示和可发现性；
- REPL 的本地 Alda 操作与模型服务共同初始化，模型配置异常时也会妨碍已有版本的播放、导出和
  重新采用。

这些是源码可验证的现状，不等同于已经选定解决方案。

## 需求边界

下一迭代需要让用户在创作、等待、校验、试听、修改和恢复之间始终清楚“当前在哪里、发生了什么、
下一步能做什么”，并降低输入与命令操作成本。设计至少应覆盖：

- 输入编辑、历史和常用命令发现；
- 长时间模型生成及自动修正期间的阶段与进度反馈；
- 模型说明、校验结果、错误和系统状态的视觉层级；
- 当前项目、版本、约束、播放和待澄清状态的可见性；
- 中断、失败和恢复后的可操作提示；
- 模型不可用时，已有有效版本仍能执行纯本地操作。

项目尚未发布，不需要兼容现有 REPL 命令。若破坏性修改或重构能显著简化交互、澄清职责边界，可以
直接替换旧接口，不保留兼容别名或弃用周期。命令设计至少应明确区分：

- Agent 操作：自然语言创作、修改、澄清和继续修正；
- Alda 工具操作：校验、播放、停止和导出，不访问模型、不修改项目版本；
- 项目操作：状态、版本切换、采用外部乐谱和持久化设置。

目前不预设必须采用全屏 TUI、特定终端框架或 GUI。应先把真实使用中的关键摩擦转化为少量交互场景，
再选择能满足场景的最简单实现。

界面信息至少应形成两个可独立使用的视图：

- 项目视图：展示项目事实、当前版本、版本历史、约束和本地工具能力；
- 对话视图：展示用户与 Agent 的对话、澄清状态、生成阶段和 Agent 内部工具过程。

CLI 可以把项目摘要嵌入对话提示符，但不能把两个视图及其领域逻辑继续耦合在 REPL 实现中。方案应提供
不依赖终端控件的应用动作和只读视图数据，使后续 GUI 能直接复用，而不是重新实现项目或 Agent 流程。

首版一个 Project 对应一条持久对话。创建项目只建立作品上下文，不进入独立的素材录入向导，也不发起
模型请求；第一条自然语言消息成为对话首条消息和首次创作请求。打开已有项目时恢复这条对话。暂不增加
一个项目内的多会话选择和管理。

## 完成判定

具体设计形成后需要补充可观察的验收场景。最终至少应由用户再次完成“打开项目 → 创作或修改 →
观察校验 → 试听 → 查看/恢复/导出”的完整流程，并确认常用操作易发现、长任务状态清楚、输入编辑
自然、错误后知道如何继续。
