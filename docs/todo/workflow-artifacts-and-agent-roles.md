# Workflow 产物与 Agent 角色派生

> 已完成基础：[可组合指示系统首期](../iter/composable-instructions/README.md)
>
> 状态：候选方向，需由真实任务触发

## 当前边界

当前系统已经具备确定性的指示编译、固定内建 Workflow、显式启用的 Advisory Skill、项目偏好和整体
fingerprint。Skill 只影响模型输入；Alda 校验、工作乐谱写入和版本接受仍由宿主强制。

尚未实现：

- 结构化 Workflow 步骤和中间产物；
- 可重建某次模型输入的 Run/Invocation 快照；
- Role、能力 grant 和 Agent fork；
- 外部 Workflow、Skill 脚本或通用工作流运行时。

这些能力不能仅因架构上可扩展而加入。长篇任务已经证明“稳定段落与局部修改契约”有价值，但尚未证明
多 Agent 能改善质量、成本或上下文隔离。

[长篇作曲质量与可控修改](long-form-composition-quality.md) 已给出第一个真实的结构化状态需求：让
`form_plan` 随工作乐谱、恢复候选和版本保存。它是作品状态的一部分，不需要先抽象为通用 Artifact、Run
或 Workflow；只有第二类独立任务也需要相同生命周期时，再提取公共模型。

## 演进顺序

### 1. 结构化产物

仅在自然语言对话无法稳定保存必要中间状态时，引入任务所需的最小产物，例如段落计划、修改契约或评审
报告。产物必须有稳定 ID、类型、来源、内容摘要和明确生命周期，并由 Project 作为唯一持久事实来源。

### 2. 运行快照

仅在需要解释指示变更导致的行为差异或可靠重放时，保存本次实际生效的指示 fingerprint、模型配置引用、
输入产物摘要和输出引用。不得复制密钥，也不得把供应商临时工具轨迹提升为项目事实。

### 3. Role 与 fork

只有同一 Workflow 已由单 Agent 稳定执行，且对照实验表明拆分角色能改善质量、成本或上下文隔离时，才
引入 Role/fork。角色能力只能是宿主授权的子集；子 Agent 不能接受版本、绕过校验或通过提示扩大权限。

外部 Workflow、脚本执行和通用调度器在出现独立需求前不设计。

## 不变量

- Skill 描述工作方法，不拥有项目状态或运行权限；
- Project 是偏好、工作乐谱、版本和持久产物的唯一事实来源；
- 核心协议与安全约束只能由宿主累加或收紧；
- 自然语言规则按稳定顺序组合不等于冲突已解决；
- 角色拆分不能改变显式接受候选、校验门禁和副作用边界。

## 启动实现的证据门槛

- 至少一个重复出现的真实任务无法仅靠现有对话、工作乐谱和 Skill 稳定完成；
- 能明确指出缺失的是产物、快照还是上下文/能力隔离，而不是笼统要求“支持 Multi-Agent”；
- 最小原型有可比较的单 Agent 基线和验收指标；
- 若原型没有带来可测收益，直接撤回该抽象。
