# Alda Music Agent 首期需求文档

> 状态：首期基线已确认
>
> 日期：2026-08-05
>
> 范围：用于验证核心创作闭环的首期版本

## 1. 产品定义

Alda Music Agent 是一个面向音乐创作的垂直 Agent。用户可以提供诗歌、情绪、意象、叙事或
直接的音乐要求，Agent 将其理解并发展为可播放、可修改、可导出的音乐作品。

首期产品验证“非音乐素材能否通过自然语言转化为完整器乐作品”。它不要求用户理解 Alda
语法、调性、和声、曲式或配器，也不以基础设施完整度作为进度指标。

核心闭环为：

```text
创作素材与要求
→ Agent 解读和音乐构想
→ 生成 Alda 作品
→ 客观校验与自动修正
→ 播放
→ 用户自然语言反馈
→ 局部或整体修改
→ 保存和导出
```

## 2. 设计约束

产品设计和实施遵守仓库根目录 `AGENTS.md` 中的原则：

1. 简单，直到不能更简单；
2. 真实闭环优先；
3. 先验证，再抽象；
4. 只解决已经存在的问题；
5. 纵向切片，小步交付。

新增功能、抽象和基础设施必须能够直接改善当前闭环，或者解决已经复现的问题。

## 3. 目标用户

首期用户是愿意在 Linux 终端中使用本地工具的音乐爱好者或程序员。他们可能缺少系统的乐理、
作曲和 Alda 知识，但能够描述自己的感受、素材和创作目的。

典型用户希望：

- 把一首诗、一段文字或一种印象发展成音乐；
- 不学习 Alda 语法也能得到可播放作品；
- 试听后用日常语言修改作品；
- 查看、恢复和导出有效版本；
- 在需要时指定或排除乐器。

## 4. 首期核心场景

### 4.1 灵感驱动的器乐创作

用户输入诗歌等非音乐素材，并要求创作完整曲目或即兴片段。Agent 应当：

1. 解读素材的意象、情绪、节奏和变化；
2. 给出简短、可理解的音乐构想；
3. 根据素材自动选择配器并说明理由；
4. 生成纯器乐 Alda 作品；
5. 使用可用工具检查作品并自动修正客观错误；
6. 让用户播放并以自然语言反馈；
7. 根据反馈修改整首、明确段落或明确乐器；
8. 保留每个通过校验的版本并支持导出。

### 4.2 作品尺度

首期支持两种创作意图：

- **完整曲目**：通常约 2–5 分钟，具有可感知的开始、发展和结束，或者满足明确的循环结构；
- **即兴片段**：通常为几十秒至约 2 分钟，可围绕单一意象或材料自由发展，并能独立播放。

上述长度是创作目标，不是无条件的精确限制。用户给出明确时长要求时，Agent 应使用可用工具
检查；用户使用“大约”“左右”等表述时，允许合理偏差并说明实际结果。

### 4.3 完整性的含义

完整作品至少应满足：

- 有明确的整体音乐构想；
- 有可感知的结构或发展过程；
- 配器和主要音乐材料前后一致；
- 可以从头到尾播放；
- 不是孤立和弦、未发展的短句或被意外截断的输出。

艺术上的完整感最终由用户试听判断，不能由语法检查或模型自评替代。

## 5. 交互需求

### 5.1 首期界面

首期使用单进程交互式 CLI/REPL，不启动本地服务，也不依赖 HTTP、WebSocket 或 PWA。

用户可以：

- 在终端中粘贴多行素材；
- 从文本文件读取素材；
- 使用普通自然语言提出创作要求和修改意见；
- 看到 Agent 的流式文本、简短解读、创作进度和校验结果。

首期至少提供以下明确命令，具体拼写可在 CLI 设计时微调：

| 命令 | 用户结果 |
|---|---|
| `/play` | 播放当前有效版本 |
| `/stop` | 停止当前播放 |
| `/export` | 导出当前版本的 Alda 与 MIDI |
| `/history` | 查看有效版本及修改摘要 |
| `/restore` | 以指定旧版本作为新的工作基线 |
| `/quit` | 退出当前交互 |

### 5.2 解读与确认

Agent 在创作前展示简短的素材解读和音乐构想，但默认不等待用户确认，直接继续创作。

只有缺失信息会显著改变作品方向时才询问用户。用户可以在作品生成后纠正解读并要求修改。
该流程是首期产品假设；如果真实使用中频繁因解读偏差返工，应重新评估是否增加创作前确认。

### 5.3 单一候选

首期每次只生成一个作品或一个修改结果。用户不满意时，通过反馈继续修改或明确要求另一种
诠释。默认不生成候选集、自动 A/B 或多角色协作。

其他创作流程可以在后续以扩展或 Skill 形式出现，但首期不预先实现通用 Skill 框架。

## 6. 创作与配器需求

### 6.1 自动配器

用户未指定乐器时，Agent 根据素材的意象、情绪、结构和目标长度自动选择配器，并简要说明：

- 选择了哪些乐器；
- 每件乐器在作品中的作用；
- 配器如何对应素材的主要变化。

说明应面向缺少乐理知识的用户，不能只罗列专业术语。

### 6.2 用户约束

用户可以：

- 指定必须使用的乐器；
- 排除不希望出现的乐器；
- 在修改时要求增加、删除或突出某件乐器。

明确的用户约束优先于 Agent 偏好。若 Alda 不支持指定乐器，或要求无法可靠完成，Agent 必须
说明限制并提出替代方案，不能静默替换。

后续修改默认保持已有配器的连续性，除非用户明确要求改变，或修改目标确实需要调整配器。

## 7. 校验与自动修正

### 7.1 校验层次

每次生成或修改后，Agent 使用当前可用的方法和工具检查作品。

#### 基础有效性

以下检查必须通过，结果才能成为新的当前有效版本：

- Alda 语法可以解析；
- 作品能够被 Alda 正常处理；
- 使用的乐器标识有效；
- 作品不为空且未明显截断。

#### 可测量要求

存在可靠方法或工具时，自动检查：

- 实际或估算时长；
- 是否包含用户指定的乐器；
- 是否出现用户排除的乐器；
- 声部数量；
- tempo、段落或其他明确数值要求；
- 后续工具能够可靠支持的音域、节拍和结构要求。

#### 主观要求

诗意、情绪、审美、配器效果和完整感不能伪装成客观通过项。Agent 可以解释自己的选择，
但最终由用户试听判断。

### 7.2 检查结果

每项检查至少显示以下状态之一：

- `通过`：工具提供了支持结论的结果；
- `失败`：工具确认未满足要求；
- `未检查`：当前没有可靠方法或工具。

没有工具支持时不得默认通过。首期只需要清楚的检查结果列表，不建立通用 Evidence 系统。

### 7.3 要求强度

- 明确要求失败时必须尝试修正，例如“不要使用打击乐”；
- 近似目标允许合理偏差，但应显示实际结果，例如“大约三分钟”；
- 主观偏好只指导创作，不产生虚假的客观 Pass，例如“像雨夜一样安静”。

### 7.4 自动修正

可检查要求失败时，Agent 应：

1. 把工具错误反馈给模型；
2. 自动修改作品；
3. 重新执行相关检查；
4. 首期最多自动修正 3 轮；
5. 达到上限后允许用户显式要求继续尝试。

### 7.5 失败保护

达到修正上限仍未通过时：

- 不创建新的有效版本；
- 不覆盖当前有效作品；
- 向用户说明主要失败原因；
- 当前有效版本仍可播放和导出；
- 失败草稿不进入普通版本历史，开发模式可以保留用于排查。

Provider、网络或 Alda 不可用时，应明确说明外部能力不可用，不能把它描述成作品质量问题。

## 8. 修改与版本需求

### 8.1 自然语言修改

用户可以要求修改：

- 整首作品；
- 能够明确识别的段落；
- 明确乐器或声部。

例如：“高潮更强烈”“缩短开头”“让大提琴在第二段更突出”。目标明确时只修改相关部分，
并尽量保持其他内容不变；范围不清楚时先询问用户，不能猜测高风险的局部范围。

### 8.2 有效版本

- 第一个通过必要检查的作品成为版本 1；
- 每次成功修改产生新版本；
- 既有版本不被后续修改覆盖；
- 历史显示版本号、创建时间和简短修改摘要；
- 恢复旧版本后产生的新修改仍创建新版本，不改写历史；
- 用户始终可以播放和导出当前选中的有效版本。

首期不实现分支、Take、合并、CAS 或事件溯源。

### 8.3 人工编辑

Alda 源码对用户可见，但普通用户不需要直接编辑。高级用户手工修改源码后，可以通过一个明确
命令要求 Agent 重新读取、校验并采用；首期不要求自动监控外部文件变化。

## 9. 项目与本地保存

### 9.1 项目边界

- 一个目录对应一个音乐项目；
- 不建立全局项目数据库；
- 用户通过普通目录操作复制、移动、备份或删除项目；
- 在项目目录中再次启动 Agent 时，可以恢复并继续创作。

### 9.2 保存内容

项目至少保存：

- 用户输入的原始素材；
- 用户明确提出的创作要求与乐器约束；
- Agent 当前采用的素材解读与音乐构想；
- 每个通过必要检查的 Alda 版本；
- 当前选中的版本；
- 各版本的检查结果与修改摘要；
- 已导出的 MIDI；
- 足以继续修改的会话记录。

作品事实使用清楚、可读的项目文件保存。首期不引入数据库、追加日志、checkpoint、control WAL
或复杂崩溃恢复。

## 10. 播放与导出

每个成功作品至少提供：

- 通过本机 Alda 播放当前版本；
- 停止当前播放；
- 保存 `.alda` 源文件；
- 导出 MIDI；
- 显示简短创作说明和检查结果。

首期不提供 WAV、MP3、专业音频渲染、五线谱导出或出版级排版。MIDI 和本机播放的实际声音
可能随设备和环境变化，产品不承诺可重复音频结果。

## 11. 模型接入

首期使用：

- OpenAI-compatible 请求与响应格式；
- DeepSeek 模型；
- 可配置的 `base_url`、模型标识和 API key 环境变量；
- 一个具体客户端实现。

首期应验证：

- 流式文本输出；
- 工具调用或可稳定解析的结构化工具请求；
- 在诗歌、当前要求、Alda 乐谱和校验错误共同存在时完成连续修正；
- 生成较长 Alda 作品时的输出完整性。

实现只使用实际验证过的 OpenAI-compatible 最小字段子集，不假定兼容全部 OpenAI API。
第二个真实模型接入前不提取通用 Provider 框架。

## 12. 平台、依赖与安装

### 12.1 首发平台

首期只支持 Linux。其他操作系统等待真实需求出现后再验证。

### 12.2 依赖脚本

仓库提供 Linux 安装或检查脚本，至少负责：

- 检查必要的 Java 运行环境；
- 安装或检查 Alda；
- 检查 Alda 版本；
- 检查播放链；
- 检查 MIDI 导出能力；
- 检查从源码开发所需的 Rust 工具链；
- 对缺失依赖给出可执行的修复说明；
- 安装后运行基本健康检查。

脚本不静默修改用户 shell 配置，不隐藏需要用户权限的操作，也不扩展成跨平台通用环境管理器。

## 13. 隐私与安全底线

- DeepSeek API key 只从环境变量读取，不写入项目、日志或导出文件；
- 首次使用应明确提示诗歌、创作要求、当前乐谱和校验错误会发送给配置的模型服务；
- 文件读写限制在当前项目目录和明确导出目标；
- Alda 子进程具有超时、取消和输出上限；
- 用户可以使用 `Ctrl+C` 停止当前生成或修正；
- 播放由用户明确触发；
- 可恢复错误不得导致整个程序 panic。

首期不建立细粒度 Permission Broker、审批缓存或持久 outbox。

## 14. 非目标

首期明确不包括：

- 为诗词谱曲、自动填词、人声旋律和歌词音节对齐；
- 游戏 BGM、角色主题和循环音乐的专用工作流；
- 弦乐四重奏、交响曲等专业编排工作流的完整保证；
- 默认多候选、A/B、分支、Take 和多 Agent；
- Web、PWA、本地服务、HTTP 或 WebSocket；
- 多 Provider 框架；
- Skill、Plugin、Hook、MCP 和长期 Memory 框架；
- WAV、MP3、专业音频渲染和五线谱编辑器；
- 多用户、多客户端、云同步和发布；
- 数据库、事件溯源、control WAL、checkpoint 和 production 级崩溃一致性；
- 用模型自评或自动指标证明作品“好听”。

这些能力只有在核心闭环验证成功并出现真实需求后才进入后续阶段。

## 15. 首个端到端验收场景

### 15.1 输入素材

《机械硬盘之诗》

——纪念我被烧坏的两块硬盘

> 飞旋，飞旋！
>
> 在区块间架起长桥。
>
> 吉比特生民，勿复沉眠于这银白冰冷之海
>
> 在那漆黑天穹之下
>
> 磁通，呲呲呼唤着电压，驱动宏伟悬臂
>
> 看见我们吧！
>
> 加速，加速
>
> 接引我们升入明亮天国！

### 15.2 创作目标

- 将诗歌作为灵感创作纯器乐作品；
- 目标为约 2.5–4 分钟的完整曲目；
- 自动解读机械运动、冰冷沉眠、呼唤、加速和升入天国的情绪变化；
- 自动选择配器并说明理由；
- 不等待确认，直接进入创作。

### 15.3 验收步骤

1. 用户在 Linux 项目目录启动交互式 CLI；
2. 用户粘贴诗歌并提出创作要求；
3. Agent 展示简短解读和配器理由；
4. Agent 生成作品，执行 Alda 语法、时长和配器检查；
5. 客观检查失败时，Agent 在上限内自动修正；
6. 首个有效版本保存为版本 1；
7. 用户播放完整作品；
8. 用户反馈：“让中段更冰冷、更机械，结尾的加速和明亮感更强”；
9. Agent 修改相关部分，尽量保持其他内容不变；
10. 新结果通过必要检查并保存为版本 2；
11. 用户可以查看历史、恢复版本 1，并重新选择版本 2；
12. 用户导出版本 2 的 `.alda` 和 MIDI；
13. 退出并重新进入项目后，当前版本、素材、要求和历史仍可恢复。

### 15.4 判定标准

通过条件：

- 用户不需要手工修复 Alda 语法；
- 至少产生一个可以从头到尾播放的有效作品；
- 检查结果能区分通过、失败和未检查；
- 失败尝试不覆盖已有有效版本；
- 局部修改生成新版本；
- 历史、恢复、播放与导出可用；
- 重启后可以继续项目；
- API key 未写入项目文件或日志。

不固定具体旋律、调性和配器，也不以模型自评决定艺术质量。最终听感由用户人工验收。

## 16. 后续方向

核心闭环验证后，可以根据真实需求逐项扩展：

- 游戏 BGM、场景音乐、角色主题和循环结构；
- 弦乐四重奏、交响曲和复杂多声部工作流；
- 同一素材的多种诠释、候选比较和盲听；
- 以扩展或 Skill 表达特定风格与工作流；
- 诗词谱曲、歌词创作与人声处理；
- Web 等更适合普通用户的界面；
- 额外模型与 Provider；
- 在真实故障和规模需求出现后增加相应的可靠性机制。

## 17. 待原型验证

以下问题不扩大首期范围，但必须在对应实现切片中用真实程序验证：

1. DeepSeek 模型标识、流式输出、工具调用和长内容输出的实际兼容性；
2. Alda 作品时长的可靠计算或推导方法；
3. Linux 上 Alda 播放、停止和 MIDI 导出的实际行为；
4. 安装脚本支持的 Java 与 Alda 版本范围；
5. 完整曲目生成采用一次输出还是分段生成更可靠；
6. 三轮自动修正是否能在可接受的时间和成本内解决主要失败。
