# Alda Music Agent 产品需求文档

> 状态：Draft  
> 日期：2026-07-30  
> 适用范围：产品目标、功能范围与验收基线  
> 不包含：具体 UI 设计、API Schema、Rust 类型和开发排期

## 1. 产品概述

Alda Music Agent 是一个面向音乐创作的垂直 Agent。用户用自然语言描述创作意图，Agent 生成或修改 Alda 乐谱，完成确定性校验、结构分析、版本管理和试听，并根据用户对确切版本的反馈继续迭代。

产品以 Web/App 为主要交互界面，同时提供 CLI，用于开发调试、自动化、评测和高级用户工作流。所有客户端共享同一套作品状态和 Agent 能力，不形成互不兼容的独立实现。

产品的核心价值不是“让模型输出一段乐谱文本”，而是建立可信、可恢复、可比较的创作闭环：

```text
创作意图
→ 约束与待确认问题
→ 乐谱候选
→ 确定性校验与分析
→ 版本化保存
→ 试听与反馈
→ 修改、选择或接受
```

## 2. 产品目标

### 2.1 必须实现

1. 用户无需掌握 Alda 语法，也能完成一次从创作要求到试听反馈的闭环。
2. 每次作品修改都有明确版本，能够比较、回退和追溯来源。
3. 语法、结构等客观结果与用户审美意见分开记录。
4. 用户反馈绑定确切版本、渲染结果和实际试听范围。
5. Web/App 与 CLI 使用同一作品数据、Session 和权限规则。
6. 对话压缩、客户端断线或进程重启不能改变已经提交的作品事实。
7. 人类保留接受作品和发布作品的最终决定权。

### 2.2 成功表现

- 用户可以清楚回答“当前听的是哪个版本”。
- Agent 修改失败时，不会覆盖最后一个可用版本。
- 用户可以看到硬约束是否通过，以及哪些判断仍需人工确认。
- 用户离开后可以恢复项目、版本、试听和反馈记录。
- 同一任务可以重复评测，并区分事实结果、模型判断和人类意见。

## 3. 非目标

首期不承诺：

- 专业实时伴奏或演出级低延迟；
- 替代 MuseScore、Dorico 或 DAW 的全部编辑能力；
- 完整 MusicXML/Alda 双向编译器；
- 用自动指标或 Audio Critic 证明作品“好听”；
- 默认开放 Bash、网络、DAW 写入、外设控制或发布；
- LLM 输出逐 token 可重复；
- 自动相似度分析能够给出法律结论；
- 多 Agent 一定比单 Agent 创作质量更高。

## 4. 目标用户与场景

| 用户 | 主要需求 |
|---|---|
| 音乐初学者 | 用自然语言完成短作品，并理解 Agent 做了什么 |
| 程序员音乐爱好者 | 同时使用 Alda 源码、结构分析和自动化能力 |
| 作曲/编曲学习者 | 生成候选、比较版本、试听并逐步修改 |
| 高级创作者 | 使用 CLI、Skill、MCP、外部工具和可审计工作流 |

首期核心场景：

1. 从自然语言生成一段短作品；
2. Agent 根据 parse 错误自动修正；
3. 用户试听后要求修改某个片段或声部；
4. 比较两个 Take 并选择其一；
5. 恢复历史项目并继续创作；
6. 导出可继续使用的作品 Artifact。

## 5. 产品界面

### 5.1 Web/App

Web/App 是主要产品界面，应支持完整创作闭环，而不是只显示 Agent 聊天内容。

必须提供：

- 项目、版本和当前状态；
- 创作要求、约束和未决问题；
- Agent 流式输出、工具状态和审批请求；
- 区别于纯代码编辑器的曲谱预览/编辑工作面；
- 播放、停止、片段试听、版本比较和反馈入口；
- 断线后的状态恢复。

曲谱工作面的具体记谱形式、直接编辑深度和双向映射方案尚未确定，需要专项设计与用户验证。

### 5.2 CLI

CLI 必须支持：

- 启动、恢复和查看 Session；
- 提交创作或修改请求；
- 查看流式事件、校验结果和错误；
- 批量生成和运行评测；
- 以明确退出码和结构化输出服务脚本；
- 在能力允许时执行本地播放。

CLI 与 Web/App 必须使用相同的业务规则和协议语义。CLI 不得成为唯一持有作品真相的进程。

### 5.3 多端一致性

- Connection、Session 和 Project 是不同生命周期。
- 客户端断线不等于删除 Session 或取消作品。
- 多个客户端查看同一项目时，提交必须检测版本冲突。
- 客户端能力按连接声明，例如曲谱预览、MIDI 播放、文件访问和交互审批。

## 6. 核心产品对象

| 对象 | 含义 |
|---|---|
| Project | 一项长期存在的音乐创作 |
| CreativeBrief | 用户意图、用途、风格、编制和未决问题 |
| ConstraintSet | 硬约束、软偏好及其验证方式 |
| Session | 用户与 Agent 的工作上下文 |
| Turn | 一次用户请求及 Agent 执行过程 |
| ScoreRevision | 不可覆盖的作品版本 |
| Take | 用于比较和选择的候选版本 |
| Artifact | Alda 源码、解析数据、MIDI、未来音频等内容 |
| Audition | 对某一版本和 Artifact 的确切试听 |
| Feedback | 绑定试听范围的人类意见 |
| Evidence | 语法、结构、启发式、模型或人类证据 |

## 7. 功能需求

优先级定义：

- **P0**：正式最小产品必须具备；
- **P1**：进阶产品能力；
- **P2**：Studio 或探索能力。

### 7.1 项目与创作意图

| ID | 优先级 | 需求 |
|---|---|---|
| FR-01 | P0 | 用户可以创建、打开、命名和继续一个 Project。 |
| FR-02 | P0 | 系统保留用户原始意图，并形成可版本化 CreativeBrief。 |
| FR-03 | P0 | 影响硬约束的未知项必须询问用户，不能静默猜测。 |
| FR-04 | P0 | 用户可以查看当前 Brief、约束、来源和未决问题。 |

### 7.2 生成、修改与校验

| ID | 优先级 | 需求 |
|---|---|---|
| FR-05 | P0 | Agent 可以根据 Brief 生成 Alda 乐谱。 |
| FR-06 | P0 | Agent 可以根据 parse 错误自动修正，失败时保留最后可用版本。 |
| FR-07 | P0 | 系统提供写谱、解析、分析和试听四条基础工具路径。 |
| FR-08 | P0 | 所有候选必须记录语法和适用结构检查结果。 |
| FR-09 | P0 | Hard Constraint 未通过时不能标为可接受，除非用户明确 Waive。 |
| FR-10 | P0 | 主观规则允许返回 Unknown 或 NeedsHumanReview，不得伪装成 Pass。 |
| FR-11 | P0 | 用户可以要求修改整首、可靠声部、Marker 范围或已确认片段。 |
| FR-12 | P0 | 系统支持转调、节奏、配器、动态等基础语义 MusicPatch。 |

### 7.3 版本与候选

| ID | 优先级 | 需求 |
|---|---|---|
| FR-13 | P0 | ScoreRevision 创建后不可覆盖。 |
| FR-14 | P0 | 每次修改记录父版本、生成者、Brief 版本、Artifact 和证据。 |
| FR-15 | P0 | 用户可以查看历史、比较版本、回退和接受指定版本。 |
| FR-16 | P0 | 候选修改失败不得污染 canonical 版本。 |
| FR-17 | P0 | 并发提交必须带基线 Revision，并以冲突结果拒绝过期写入。 |
| FR-18 | P0 | 用户可以创建多个 Take 并进行受控 A/B 比较。 |

### 7.4 曲谱、试听与反馈

| ID | 优先级 | 需求 |
|---|---|---|
| FR-19 | P0 | Web/App 提供独立的曲谱预览/编辑工作面；具体实现待专项裁决。 |
| FR-20 | P0 | 用户可以播放、停止和试听指定版本或片段。 |
| FR-21 | P0 | 每次 Audition 记录 Revision、Render、播放范围、客户端和结果。 |
| FR-22 | P0 | 用户停止播放时，系统记录实际 played range，反馈不得自动扩展到未播放范围。 |
| FR-23 | P0 | 用户可以对一次确切 Audition 提交结构化或自然语言反馈。 |
| FR-24 | P0 | Agent 不得声称自己听到了未经过音频模型或人类反馈的声音。 |
| FR-25 | P1 | 系统支持盲式 A/B，隐藏候选生成者并平衡播放顺序。 |
| FR-26 | P0 | 系统提供可听差异与符号差异摘要，但不代替人耳判断。 |

### 7.5 Session 与多端协议

| ID | 优先级 | 需求 |
|---|---|---|
| FR-27 | P0 | 用户可以启动、恢复、引导和取消 Turn。 |
| FR-28 | P0 | Web/App 和 CLI 通过统一、版本化的双向协议访问 Runtime。 |
| FR-29 | P0 | 协议支持客户端请求、服务端事件和服务端发起的审批/询问。 |

| FR-32 | P0 | 对话压缩只压缩模型上下文，不改写作品版本、约束和反馈。 |
| FR-33 | P0 | 流式过载必须显式报告，不得静默丢失权威状态事件。 |

### 7.6 Provider、Artifact 与互操作

| ID | 优先级 | 需求 |
|---|---|---|
| FR-34 | P0 | Runtime 支持至少一个可用模型 Provider；工程基线验证 Anthropic 与 OpenAI 适配。 |
| FR-35 | P0 | Provider 差异在适配层归一化，不能泄漏为两套产品行为。 |
| FR-36 | P0 | Alda 源码、解析结果和 MIDI 作为带 hash 的 Artifact 保存。 |
| FR-37 | P0 | 用户可以查看和导出当前已接受版本的可用 Artifact。 |

| ID | 优先级 | 需求 |
|---|---|---|

| FR-41 | P0 | 所有副作用在发生前完成权限判断和必要审批。 |
| FR-42 | P0 | 审批展示动作、目标、范围和预计影响，而不是只展示工具名。 |
| FR-43 | P0 | 客户端断线或取消后，子进程和播放资源必须得到清理。 |
| FR-44 | P0 | 浏览器和普通客户端不能读取模型密钥或服务端凭据。 |
| FR-45 | P0 | 只有人类可以最终 Accept 或 Publish。 |

## 8. 非功能需求

### 8.1 可靠性

- 作品和证据使用持久化事件或等价可恢复机制保存。
- 写入采用原子提交；损坏尾记录不得破坏此前有效数据。
- 长任务支持取消、超时和进程组清理。
- 内部队列必须有界；过载返回可识别、可重试错误。
- 状态恢复不依赖再次调用模型生成相同内容。

### 8.2 安全与隐私

- 秘密只来自环境变量或凭据存储，不进入 Project、Rollout 或 Memory。
- 路径必须限制在授权根目录，并防止路径穿越和符号链接逃逸。
- 遥测默认关闭；完整 Prompt、乐谱、音频和 Memory 默认不上传。
- 模型调用属于数据外发，首次使用前必须说明 Provider、发送字段和政策。
- Audio Critic 单独 opt-in，不能沿用文本模型授权。

### 8.3 易用性

- 核心创作闭环不要求用户阅读 Alda 源码。
- 所有失败都说明发生了什么、作品是否安全以及下一步选择。
- Web/App 清楚展示当前 Project、Revision、约束、试听对象和权限状态。
- CLI 区分 stdout 数据与 stderr 错误，并使用稳定退出码。

### 8.4 性能与可观测性

- 记录首个流式输出时间、首次可试听时间、Turn 时长、成本和失败率。
- 发布前建立真实设备和真实网络下的性能基线；具体 SLA 需经原型确定。
- 常规日志只记录 ID、hash、安全摘要、时延、状态和大小。
- 性能优化不能牺牲 Revision、审批或反馈链的正确性。

### 8.5 兼容性

- Application Protocol、Session 和 Evaluation Report 必须带 schema version。
- 协议升级必须提供兼容期或明确迁移路径。
- 客户端根据能力协商功能，不假定所有设备都能播放、上传或访问文件。
- 首发支持的平台和浏览器范围在产品化前单独冻结。

## 9. 评测要求

正式产品使用 `alda-eval/v2`：

| 层 | 验证内容 |
|---|---|
| H0 | 文件、hash、Alda parse、Artifact 完整性 |
| H1 | 硬约束、音域、时长、节拍、编制 |
| H2 | 变形正确性与 metamorphic tests |
| H3 | 动机、段落、结构与 Brief adherence |
| H4 | 盲式 LLM Judge，仅作辅助信号 |
| H5 | 人类 A/B，允许无偏好或不确定 |
| H6 | 多样性、来源、相似风险和动机谱系 |
| H7 | 时延、成本、失败率和取消清理 |

评测报告不得用单一总分掩盖事实失败、主观分歧或未知项。

## 10. 阶段与完成定义

### 阶段 A：工程基线（M0–M5）

交付单 Agent、双 Provider 适配、四个工具、Session 恢复、压缩和 legacy H0–H3 评测。该阶段证明 Agent 闭环可运行，不等于正式最小产品。

### 阶段 B：正式最小产品（M6–M8）

交付 Brief、Constraint、不可变 Revision、Artifact、Tool V2、权限、Take、Audition、Feedback，以及 Web/App 与 CLI 共用的最小协议纵切片。

完成标准：用户能够从需求出发，得到合法版本，在主要界面预览并试听，对确切片段反馈，生成新 Revision，最终由用户接受一个可恢复版本。

### 阶段 C：Advanced（M9–M10）

交付模式、MUSIC.md、Skill、声明式 Hook、本地 Plugin、只读 MCP 和证据化 Memory。

### 阶段 D：Studio/探索（M11–M12+）

验证隔离 SubAgent、多 Agent 收益、完整质量闭环，以及 DAW、外设和受限写入扩展。

## 11. 最小产品验收场景

正式最小产品必须完整通过以下场景：

1. 用户在主要界面创建项目并输入一段明确创作要求；
2. 系统展示 Brief、硬约束和需要确认的问题；
3. Agent 生成乐谱，自动修复 parse 错误并创建 Revision；
4. 用户在曲谱工作面查看作品并试听一个明确范围；
5. 系统记录实际播放范围，用户提交“这一段太密”等反馈；
6. Agent 基于原 Revision 创建新版本，不覆盖旧版本；
7. 用户比较版本并接受其中一个；
8. 客户端断线或进程重启后，项目、版本、试听、反馈和接受状态均可恢复；
9. CLI 可以读取同一项目并得到一致状态；
10. 未经审批的播放、越界写入、联网或发布均不可发生。

## 12. 待决策事项

以下问题不阻塞需求冻结，但必须在对应实现开始前裁决：

1. 首发采用本地 Web/PWA、云托管、桌面壳还是混合模式；
2. 曲谱预览采用何种表示，首期提供多少直接编辑能力；
3. 浏览器使用 MIDI 播放、离线音频还是两者并存；
4. Application Protocol 采用 JSON-RPC、tagged message 或 ACP 子集；
5. 所有客户端离线后，运行中的 Turn 保留多久；
6. 首期是否只支持单用户单写，何时引入多人协作；
7. 首发操作系统、浏览器和移动平台范围；
8. 正式 Beta 的时延、成本和可用性目标。
