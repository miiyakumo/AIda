# CLI 交互体验改进方案

> 需求来源：[CLI 交互体验改进](../../todo/cli-ergonomics.md)
>
> 方案日期：2026-08-13
>
> 状态：方案已形成，待评审确认

> 兼容性前提：项目尚未发布，本次允许删除和重命名现有命令，也允许为清晰的交互边界重构实现；不为
> 未形成的使用习惯保留兼容别名或弃用周期。

## 目标

本次迭代把当前“功能可调用”的逐行 REPL 改造成适合连续音乐创作的终端工作台。用户在任何时刻都应
容易回答三个问题：

1. 我在哪个项目、哪个版本和哪些约束下工作；
2. 程序正在生成、校验、修正、播放，还是等待我输入；
3. 当前结果是否安全，下一步可以做什么。

目标不是增加视觉装饰，而是降低输入、记忆和判断成本，同时保持当前单进程、线性版本和本地 Alda
工作流简单可查。信息结构上明确分离项目视图与对话视图，使终端交互不再等同于应用本身，后续 GUI
可以复用同一应用能力和状态投影。

## 非目标

本次不实现：

- 全屏 TUI、GUI、鼠标操作或固定面板布局；本次只建立可被这些界面复用的应用边界；
- 后台并行生成、生成期间继续输入或多个任务队列；
- 分支版本、多候选、一个项目内的多条 Agent 对话、会话选择器、通用 Provider 或通用 UI 事件框架；
- 无法由程序真实测量的百分比和剩余时间；
- Alda 播放进程的外部实时监控。

现有 REPL 命令不属于兼容接口。`/play`、`/history`、`/restore`、`/reload`、`/continue` 和
`/strategy` 等扁平命令将在新交互中直接删除，不保留别名。

## 方案结论

采用**增强型滚动 REPL**：保留终端原生滚动记录，在提示符中显示当前上下文，以结构化事件展示长任务
阶段，通过行编辑器提供多行输入、历史和补全。暂不采用全屏 TUI。

当前操作是串行的，生成期间也不接受新的交互输入，因此全屏布局带来的重绘、终端恢复和尺寸适配成本
没有对应收益。滚动 REPL 还能自然保留完整过程，便于回看、复制错误和比较几轮校验结果。如果后续出现
后台任务、并列候选或需要同时操作播放时间线，再重新评估全屏 TUI。

终端交互使用 `reedline` 0.49：它在项目的 Rust 1.85 基线上支持 Unicode、多行编辑、历史、提示、
补全和可定制键位。长任务的短暂活动指示使用 `indicatif` 0.18；阶段名称和结果仍由本项目定义，不能
由 spinner 文案代替。非 TTY 或设置 `NO_COLOR` 时关闭动画和颜色，保留同样的文本结构。实现时由
`Cargo.lock` 固定最终版本，并在 Rust 1.85 上执行构建验证。

## 界面信息结构：两个独立视图

应用对外提供两个独立的状态投影。这里的“视图”是只读数据，不是终端控件，也不预设未来 GUI 的框架：

| 视图 | 回答的问题 | 包含 | 不包含 |
|---|---|---|---|
| 项目视图 | “这个音乐项目现在是什么状态？” | 项目名、初始请求摘要、当前版本、版本列表、创作设置、版本检查摘要、可用的本地能力 | 模型 API 消息、流式文本、正在生成第几轮 |
| 对话视图 | “我和 Agent 进行到了哪里？” | 用户与模型消息、待澄清/可继续状态、当前 Agent 阶段、Agent 内部工具结果、建议的下一步 | 版本存储实现、项目配置修改逻辑、用户直接发起的播放和导出 |

终端默认处于对话视图：滚动区显示对话和 Agent 执行过程，输入框接受自然语言。提示符上方只嵌入一行
项目视图摘要，避免用户在对话时失去项目上下文；执行 `/project` 时输出完整项目视图。用户直接执行
`/alda play`、`/alda check` 或 `/alda export`，属于对项目产物的工具操作，其结果不写入 Agent 对话；
Agent 为生成候选而调用 Alda 校验时，则作为对话视图中的 Agent 内部工具事件展示。

未来 GUI 可以把项目视图放在侧栏或独立页面，把对话视图放在主区域，但这只是布局变化。两种界面都调用
相同的应用动作并读取相同的视图数据，不复制项目、Agent 或 Alda 逻辑：

```text
                Application
        actions / snapshots / events
              /                       \
      Terminal adapter            Future GUI adapter
  command parser + renderer       widgets + renderer
              |                       |
      ProjectView + ConversationView
```

视图不是新的事实来源。`ProjectView` 每次从 `Project` 和能力状态生成；`ConversationView` 从
`Project::conversation` 与当前前台操作生成。界面不能直接修改视图字段，只能提交应用动作，动作完成后
再获取新快照。当前不建立通用状态管理器、事件总线或 UI 组件协议；只保留两个快照查询和 Agent 长操作
所需的同步事件回调。

Alda 不形成第三个长期视图。用户直接调用 Alda 是针对项目产物的短时操作，由动作结果返回并更新必要的
项目快照；Agent 内部调用 Alda 则作为对话过程的一部分。这样工具身份清楚，但不会为当前唯一工具提前
建立工具工作台。

### Project 与 Agent 对话的关系

参考调研：[Coding Agent 的工作区与会话关系](../../research/agent-workspace-sessions.md)

Codex、Claude Code 和 Grok 都把工作目录作为会话上下文，而不是会话本身：默认启动新会话，并通过
`resume`/`continue` 恢复当前目录下的既有会话。因此同一个代码工作区可以对应多条对话，这适合在一个
仓库中处理许多彼此无关的任务。

本项目的 `Project` 边界更窄：它已经代表一首作品的设置、有效版本和连续修改过程。首版采用
**一个 Project 对应一条持久对话**，不再引入独立的 session ID、启动时的会话选择器或 `/new`、
`/resume` 命令。打开项目就是恢复它的对话；新建项目则得到一条空对话。退出终端只结束本次界面进程，
不结束或清空项目对话。

在领域模型中，`Project` 是聚合根并拥有一条 `Conversation`：普通项目字段保存设置和版本，Conversation
保存首次请求、后续对话条目和待处理的 Agent 状态。两部分由一次项目持久化共同保持一致，再分别投影为
两个视图。对话不独立装载，也不需要自己的用户可见 ID。这种所有权没有把视图重新耦合；它只明确一条
对话不能脱离作品单独存在。

## 关键交互场景

### 从 Shell 进入

Shell CLI 与项目内命令是两个界面，不共用一套扁平命令。新的 Shell CLI 只保留入口、一次性创作和
诊断：

```text
alda-agent --name NAME             # 打开或创建默认目录中的项目并进入交互
alda-agent --project PATH          # 打开或创建指定目录中的项目并进入交互
alda-agent projects                # 列出默认目录中的项目
alda-agent compose [OPTIONS]       # 一次性 Agent 创作，不进入交互
alda-agent doctor [--probe TARGET] # 检查环境；TARGET 为 model、alda 或 all
```

无子命令时直接进入交互，不再要求输入 `repl`。删除现有 `repl`、`list`、`create`、`smoke` 和
`alda-smoke` 子命令：`list` 变为更明确的 `projects`，`create` 变为避免与“创建项目”混淆的
`compose`，两个 smoke 合并为 `doctor --probe`。这是直接替换，不提供兼容别名。

交互项目的模式、时长、乐器约束和创作策略统一由 `/project config` 持久化管理，不再混入打开项目的
Shell 参数。`compose` 仍用命令行参数表达一次性任务约束，保证脚本调用无需进入 REPL。

### 打开已有项目

进入 REPL 后立即显示项目快照和下一步，而不是只打印一次项目名后退化为 `> `：

```text
mechanical-drive-poem · v2 · 完整曲目 · 180 秒 · +piano · -violin
就绪 · 输入修改要求；/alda play 试听；输入 / 后按 Tab 查看命令
›
```

第一行来自持久化的 `Project`，包括项目、当前版本、模式、目标时长和乐器约束；没有约束的字段不显示。
第二行来自当前会话状态，优先提示一个或两个最相关动作。终端较窄时允许自然换行，不为维持单行而
隐藏状态。执行 `/alda play` 后，第二行显示“已发起播放 v2 · /alda stop 停止”；停止后恢复就绪提示。

### 创建项目并开始对话

新项目不再进入独立的“素材录入模式”。项目目录和空对话建立后，直接显示普通对话提示符：

```text
mechanical-drive-poem · 尚无版本 · 完整曲目
新项目 · 描述你想创作的作品，也可以直接粘贴诗歌、故事或其他参考素材
› 根据下面这首诗创作一首逐渐明亮的机械感作品：
  ……
```

这与其他 Agent 的初始化方式一致：先确定工作上下文，再由第一条用户消息启动对话。区别是其他 coding
agent 通常把 cwd 关联到多条任务会话，而本项目把一首作品建模为一个 Project，因此打开 Project 就
确定了唯一对话。

允许没有消息和有效版本的空 Project 存在；仅创建或打开项目不访问模型。用户提交第一条非命令消息时，
该消息作为 `Conversation` 的第一条用户消息和首次创作请求，然后才发起 Agent 操作。它可以只是创作
要求，也可以同时包含粘贴的参考素材，不再要求用户理解“素材”和“要求”两个输入步骤。模型若认为信息
不足，仍可在同一对话中澄清；第一个有效版本保存后，后续消息解释为对当前作品的修改要求。

第一条消息必须在模型请求前随 Project 原子保存；网络失败或用户取消不会丢失用户输入。项目视图需要
摘要时从第一条用户消息派生，不建立重复的 brief 字段。创作方向变化直接作为后续对话消息表达。

多行编辑仍由同一输入框提供：bracketed paste 保留整段粘贴，普通 Enter 提交，Alt+Enter 或
Shift+Enter 插入换行。命令只有在去除前导空白后以 `/` 开头时才按命令解析。提交空输入只重新显示提示符，
不会创建对话消息或发起模型请求。

### 发现和执行命令

命令按职责分组，顶层不再平铺每一个动作：

```text
/alda ...     直接调用本地 Alda 工具，不访问模型
/project ...  查看和修改项目持久化状态
/help ...     按路径查看帮助
/quit         退出
```

自然语言输入就是 Agent 操作，不再为它保留只有一个子命令的 `/agent` 命名空间：

```text
让中段更冰冷、更机械                 # Agent：创作、修改或回答澄清
继续修正                             # Agent：当前对话中的普通后续消息

/alda play [VERSION]                 # 工具：播放指定或当前有效版本
/alda stop                           # 工具：停止播放
/alda check [VERSION]                # 工具：按项目约束校验指定或当前版本
/alda check --file PATH              # 工具：只校验外部文件，不采用
/alda export [VERSION] [--format alda|midi|all] # 默认当前版本和 all

/project                             # 项目：显示完整项目视图、约束和能力
/project versions                    # 项目：列出有效版本
/project switch VERSION              # 项目：切换当前版本，不删除后续历史
/project adopt PATH                  # 项目：校验外部 Alda 文件并保存为新版本
/project config                      # 项目：查看全部持久化设置
/project config mode full|improv
/project config duration SECONDS|none
/project config include INST...|none # 替换必须包含的乐器列表
/project config exclude INST...|none # 替换必须排除的乐器列表
/project config strategy TEXT|default
```

`/project adopt PATH` 取代“直接编辑 `current.alda` 后 `/reload`”的流程。该项目操作先调用 Alda 校验，
通过后才创建版本。`current.alda` 继续表示当前有效版本，不再兼作未校验草稿；外部文件校验失败时
原文件和当前有效版本都不改变。这样可以删除当前失败后覆盖人工编辑内容的危险语义。

当前只有 Alda 一个直接暴露给用户的工具族，因此使用 `/alda`，不提前设计 `/tool alda` 或通用工具
注册系统。Agent 内部自动调用 Alda 校验仍显示为 `Tool · Alda`，但这只是统一的输出语义；将来真正出现
第二个用户可调用工具族时，再依据实际关系决定是否引入 `/tool`。

`/project config` 每次只修改一个键并立即校验、持久化。`include` 和 `exclude` 是替换语义，不使用容易
产生累计误解的隐式追加；`none` 清空列表或时长，`default` 清除自定义创作策略。冲突的乐器约束在写入
前拒绝，原配置保持不变。

`/help` 显示自然语言输入及上述四个顶层入口；`/help alda` 显示 Alda 子命令；`/help alda export` 显示参数、默认值、
前置条件和示例。输入 `/`、`/alda ` 或 `/project ` 后按 Tab 分层补全；`/alda play `、
`/alda export ` 和 `/project switch ` 只补全已有版本号，`/alda check --file ` 和
`/project adopt ` 补全文件路径。

所有命令由同一份命令目录定义，解析、帮助、补全和参数提示共同使用它，避免四份列表逐渐不一致。
提示符根据状态推荐命令，例如无有效版本时提示输入创作要求，生成校验失败后优先提示
“输入‘继续修正’或新的要求”，待澄清时提示直接回答问题。输入 `/project status` 不再作为别名接受；裸
`/project` 已经承担这个入口，避免为了名词分组再增加无信息量的一层。

暂不增加菜单或命令别名。上下方向键浏览当前项目的输入历史，历史包括已提交的自然语言和命令。最近
500 条输入保存在项目目录的 `.repl-history` 中，重新打开项目后仍可使用；
损坏或不可写时告警并退化为会话内历史，不能阻止项目打开和创作。不同项目不共享输入历史。

### 观察生成、校验和自动修正

一次创作或修改以真实阶段展示进度，不显示百分比：

```text
◇ Agent · 生成第 1/3 轮 · 等待模型

模型
  我会用稳定脉冲表现机械运转，并让尾声逐渐明亮。

◇ Tool · Alda 校验 · 第 1/3 轮
✓ Alda 语法 · 解析成功
✓ 作品内容 · 4 声部，955 个可播放事件
! 时长 · 约 151 秒，目标 180 秒
✓ 包含乐器 · piano
✓ 排除乐器 · violin

↻ Agent · 自动修正第 2/3 轮 · 1 项未通过
```

等待网络响应、接收工具参数和运行 Alda 时显示活动指示；模型文本开始流式输出后，渲染器在不破坏活动
指示的情况下将其放入单独的“模型”块。每一轮候选都显示完整检查结果，使用户知道为什么发生下一轮
修正。成功后用独立结果块收尾：

```text
✓ 已保存 v3 · 2 轮完成
  当前有效版本已从 v2 更新为 v3。
  下一步：/alda play 试听，或直接输入修改要求。
```

阶段事件为应用语义，不直接来自终端动画。最小事件集合为：Agent 轮次开始、模型请求开始、模型文本
增量、候选已提交、Alda 工具开始、Alda 工具完成、Agent 将自动修正和操作完成。传输层只报告数据，
不直接写 stdout/stderr。用户直接执行 `/alda` 与 Agent 内部调用 Alda 使用同一工具结果类型；区别是
前者为顶层工具操作，后者在 Agent 轮次下缩进显示，不能把本地校验伪装成模型行为。

### 澄清、失败和继续

模型只提出问题时，问题显示为模型块，随后提示：

```text
? 等待补充信息 · 直接回答上面的问题
```

该状态继续由项目中的短期模型上下文持久化，重启后仍能恢复。校验达到轮数上限时明确说明当前有效版本
未改变，并将提示符切换为：

```text
修正未完成 · 输入“继续修正”，也可以提出新的要求
```

这两种输入都属于普通 Agent 消息，原样追加到当前 Conversation；程序不识别“继续修正”等特殊短语。
待澄清时，下一条消息自然成为问题的回答；校验失败时，下一条消息自然延续失败上下文。Agent 根据完整
对话、当前有效版本和项目设置处理，不需要隐藏的命令状态机。

### 中断当前操作

Ctrl+C 的边界从整个 REPL 收缩到当前输入或当前操作：

- 编辑输入时，Ctrl+C 清空本次输入并重新显示提示符；
- 生成、校验或导出时，Ctrl+C 取消当前操作，清理活动 Alda 子进程并回到 REPL；
- Ctrl+D 或 `/quit` 才退出 REPL。

取消完成后必须显示操作阶段、当前有效版本未改变以及可执行的下一步：

```text
! 已取消 · 生成第 1/3 轮
  当前有效版本仍为 v2，未保存候选。
  下一步：重新输入要求，或 /alda play 试听 v2。
```

每次前台操作使用独立的取消标记，不能复用当前全局 `AtomicBool`。这样旧 Alda 任务不会在下一次操作
重置取消状态后继续运行。模型 future 被取消时关闭请求；阻塞的 Alda 子进程观察该操作自己的取消标记
并终止进程组。REPL 必须等待该操作确认清理完成后再显示提示符，不能让已取消的线程在后台继续工作。
具体边界是：前台操作拥有取消标记和 Alda 阻塞任务句柄；收到信号后先设置标记，再等待阻塞任务终止。
如果仍处于 HTTP 请求阶段，则丢弃请求 future 后即可结束。不要只丢弃 `spawn_blocking` 的 `JoinHandle`，
因为这不会停止已经开始的阻塞任务。

### 模型不可用时继续本地工作

运行能力拆成三个边界：

```text
项目能力：状态、历史、恢复、Alda 源码导出
Alda 能力：校验、播放、停止、MIDI 导出
模型能力：首次创作、自然语言修改、继续自动修正
```

启动 REPL 时项目必须能够独立打开。Alda 可执行文件独立发现；模型配置可以独立检查，但模型客户端仍在
第一次模型操作时创建。配置缺失、鉴权失败或网络失败只把模型能力标记为不可用，不能阻止项目和 Alda
操作。界面区分“未尝试”“已配置”和“最近请求失败”，配置可读不等同于远端已连通。失败不会永久锁定
会话；用户再次发起模型操作时重新读取配置并重试，但程序不在同一次操作中自动重试可能产生费用的
请求。

例如 `.env` 无效但本机 Alda 可用时：

```text
mechanical-drive-poem · v2 · 完整曲目 · 180 秒 · +piano · -violin
仅本地 · 模型配置不可用；仍可 /alda、/project versions、/project switch
›
```

`/alda export` 在模型不可用时仍导出 Alda 和 MIDI。若 Alda 本身不可用，Alda 源码仍可导出，MIDI
部分单独报告未完成；播放、校验和模型创作则说明缺少 Alda，因为生成结果不能绕过有效版本校验。

## 状态模型与不变量

应用状态由几个正交维度组成，不用一个不断膨胀的总枚举表示；两个视图只是从这些状态派生：

| 维度 | 来源 | 典型状态 |
|---|---|---|
| 项目 | `Project` | 项目名、版本、模式、时长、乐器约束 |
| 项目对话 | `Project::conversation` | 消息、无待处理动作、等待澄清、可继续修正 |
| 前台任务 | 仅进程内 | 空闲、模型生成、校验、自动修正、导出 |
| 播放 | 仅进程内 | 未知、已发起播放某版本、已请求停止 |
| 运行能力 | 独立服务状态 | 未检查、已配置/已发现、最近成功、最近失败及错误 |

`Project` 仍是项目事实来源，提示符和 `/project` 都从它派生，不能维护第二份项目版本或约束状态。
项目拥有一条 `Conversation` 并与其他项目元数据一起原子持久化。当前
`Project::conversation: Vec<deepseek::Message>` 将改为供应商无关的领域类型：项目领域不能依赖某个模型
供应商的传输消息，对话视图也不能直接暴露该协议。模型适配器负责在领域消息与供应商请求之间转换。

删除现有 `source_material`、`requirements` 和累计拼接的 `interpretation` 字段；首次请求、参考素材、
后续要求和模型说明都由 `Conversation` 保存，不维护可能分叉的重复事实。项目尚未发布，不设计旧元数据
迁移。

`Conversation` 是供应商无关的完整 Agent 对话，也是后续模型请求的会话上下文；模型适配器在请求时将
领域消息转换为供应商协议，并注入当前项目设置与有效版本。用户直接执行的 `/alda`、`/project` 命令和
结果不进入该上下文。首版不实现对话压缩或摘要，等真实出现上下文长度问题后再设计。
前台任务在串行 REPL 中同时最多一个，进程异常退出后不持久化“正在生成”等瞬时状态。

播放状态只表示本次会话成功发起过 `/alda play` 或 `/alda stop`，不声称知道 Alda 播放是否自然结束，
也不推断其他进程发起的播放。界面使用“已发起播放 v2”而不是长期显示“正在播放”。

实现必须继续维护以下不变量：

1. 只有所有必要检查均未失败的候选才能成为有效版本；
2. 生成中的候选、失败候选和被取消候选不会覆盖 `current.alda`；
3. 操作失败或取消后明确指出当前有效版本，不能暗示整个项目完全未写入；
4. 模型能力失败不能连带关闭项目能力和可用的 Alda 能力；
5. 颜色、动画、终端宽度和行编辑器故障不能改变项目语义；
6. 所有终端输出经统一渲染边界产生，模型传输和领域逻辑不能自行打印。

## 输出层级和错误恢复

输出使用稳定的文字标签和符号，颜色仅作为增强：

| 类型 | 无颜色标识 | 内容 |
|---|---|---|
| 阶段 | `◇` / `↻` | 正在生成、校验或修正 |
| 模型 | `模型` | 解释文本或澄清问题 |
| 成功 | `✓` | 检查通过、保存、播放、恢复或导出完成 |
| 注意 | `!` / `?` | 检查失败、能力降级、等待输入或取消 |
| 错误 | `错误` | 操作无法完成及原因 |

错误面向用户按恢复方式分组，不要求首个实现建立通用错误框架：

- 输入或命令错误：指出错误字段、正确用法和最接近的命令；
- 前置条件不满足：说明缺少有效版本、失败上下文或 Alda，并列出当前可用动作；
- 模型配置、鉴权或网络错误：保留底层摘要，标记本地能力仍可用，不自动重试产生费用的请求；
- Alda 校验失败：显示逐项结果，保留当前有效版本；自动修正耗尽时提示输入“继续修正”或新的要求；
- 用户取消：作为可恢复结果而不是致命错误，返回提示符；
- 项目元数据损坏：拒绝打开和写入，保留现有文件并报告具体损坏位置。

## 实现边界

保留单 crate 部署形态，但允许破坏性重构当前 REPL 和模块边界。目标结构如下：

- 新增 UI 无关的 `Application` 入口，负责装载项目、执行一次用户动作，并提供
  `project_view()`、`conversation_view()` 两个只读快照；它不包含终端输入输出类型；
- `repl.rs` 降为终端适配器，只负责读取输入、调用命令解析和渲染应用结果，不再编排领域用例或维护
  项目事实；未来 GUI 从 `Application` 接入，而不是复用 `repl.rs`；
- Agent、Alda 和 Project 各有独立动作类型与执行入口；输入首先解析为这三类动作，再交给对应执行器；
- 命令目录成为解析、帮助、补全和前置条件的共同来源；
- 新增小型终端交互模块，封装 `reedline` 输入、动态提示符、TTY/`NO_COLOR` 判断、spinner 和语义渲染；
- `agent.rs` 在既有三轮循环中报告生成事件，不改变创作、澄清、校验和保存语义；
- `deepseek.rs` 移除直接 `print!`/`eprintln!`，将模型文本增量交给调用方，同时仍返回完整协议结果；
- `alda.rs` 将全局取消标记改为每次操作独立的取消上下文，耗时本地操作继续放在线程边界外执行；
- `main.rs` 不再用一次 Ctrl+C 选择包裹整个 REPL，只为一次性命令和 REPL 内的单次操作设置取消边界；
- 模型客户端与 `AldaRunner` 分开初始化和缓存；删除当前同时持有二者的 `Services`；`Application`
  明确持有项目和按需创建的能力，但不演变成通过字符串查找服务的通用容器或 Provider 抽象。

领域逻辑通过小型同步 reporter/callback 报告事件即可。当前 REPL 不并发接收输入，因此不需要 channel、
actor 或事件总线。渲染器负责在模型文本输出时暂时让出活动指示，非 TTY 时直接产生追加式纯文本。

实现中的动作类型应反映交互边界，而不是继续使用一个扁平 `ReplCommand`：

```text
UserAction
├── Agent(Prompt)
├── Alda(Play | Stop | Check | Export)
├── Project(Overview | Versions | Switch | Adopt | Config)
├── Help
└── Quit
```

Agent 可以编排 Alda 校验并在成功后请求 Project 保存版本，但不能拥有播放、导出或版本切换；Alda
动作不能初始化模型，也不能修改项目版本；Project 的 `adopt` 可以组合 Alda 校验，其余 Project 动作
只读写持久化状态。这个依赖方向既是命令分组依据，也是模型不可用时本地降级仍能工作的实现约束。

应用动作与视图保持不对称：动作表达意图，视图表达当前事实。不要为每个视图建立一套重复的命令，也
不要让 `ProjectView` 或 `ConversationView` 执行业务逻辑。最小接口形态为：

```text
Application::execute(UserAction, Reporter) -> ActionResult
Application::project_view() -> ProjectView
Application::conversation_view() -> ConversationView
```

`Reporter` 只承载一次长操作中的 Agent 阶段、文本增量和内部工具结果；项目快照变化由动作结果通知界面
重新读取，不为此引入常驻事件总线。

交互式 TTY 使用 `reedline`；非 TTY 的 REPL 使用基础逐行输入且不显示终端控制序列，不保留旧的 `.`
素材分隔协议。脚本化多行素材继续通过一次性 `compose --file` 或 stdin 工作流提交。命令解析、应用执行
和渲染数据保持可注入，使多数离线测试不依赖真实终端；另用少量 PTY 测试覆盖真实按键。

## 实施顺序

1. 先把 `Project::conversation` 改为供应商无关的领域类型，拆分 Alda 和模型能力，建立 `Application`
   与两个视图快照，并补齐模型不可用时的本地操作测试；
2. 建立语义事件和统一渲染边界，移除模型客户端直接终端输出，逐轮展示生成与校验；
3. 接入 `reedline`、动态提示符、命令目录、项目级历史、多行输入和 PTY 测试；
4. 把取消边界收缩到单次操作，替换全局取消标记并验证阻塞 Alda 任务已完成清理；
5. 完成纯文本/TTY 回归后执行真实端点与完整创作试听验收。

前两步先稳定能力和输出语义，行编辑器只负责输入体验；这样终端组件不会反向控制项目和 Agent 逻辑。

## 验收场景

### 自动化验收

至少覆盖：

1. Shell CLI 只接受新的默认交互、`projects`、`compose` 和 `doctor --probe` 接口，已删除入口解析失败；
2. 项目内命令目录生成的解析、分层帮助和补全保持一致；旧扁平命令全部被拒绝并指向新的命令路径；
3. 动作路由测试证明只有自然语言输入可访问模型，`/alda` 与 `/project` 在任何路径都不初始化模型；
4. 项目视图与对话视图可分别构造和测试；项目变化只更新项目快照，对话阶段不复制项目事实，终端适配器
   能把二者组合成提示符和 `/project` 的纯文本快照；
5. 创建空 Project 不初始化模型；首条消息在模型请求前持久化，模型失败或取消后重开项目仍能恢复；
6. 两轮生成按“Agent 生成 → Alda 校验失败 → Agent 自动修正 → Alda 校验通过 → 保存”顺序报告事件；
7. 模型配置缺失时，版本查看/切换、Alda 播放、外部文件采用和双格式导出不初始化模型；
8. Alda 缺失时 `/alda export` 仍生成 Alda 文件，并单独报告 MIDI 未导出；
9. 慢模型和慢 Alda 操作中 Ctrl+C 均返回 REPL，当前有效版本不变且 Alda 子进程在新提示符出现前被
   终止；
10. PTY 集成测试覆盖多行输入、上下历史、分层命令补全、输入中 Ctrl+C 和 Ctrl+D；
11. 非 TTY 和 `NO_COLOR` 输出没有控制序列、动画残留或缺失信息；
12. 模型文本、Agent 阶段、Alda 工具结果、项目结果和错误均通过渲染器输出，传输层不直接写终端；
13. `Project` 不再依赖 `deepseek::Message`，终端模块之外的应用测试不依赖 `reedline`，证明未来界面可从
    `Application` 执行动作并独立读取两个视图。

### 真实终端验收

由用户在 Linux 终端完成以下流程：

1. 创建新项目后直接进入普通提示符，将创作要求和多行参考素材作为首次请求粘贴、编辑并提交，
   不经过素材向导也不输入 `.`；
2. 观察至少一轮模型生成和逐项校验；若发生自动修正，能明确说出当前轮次和原因；
3. 使用上下键找回输入，输入 `/` 后通过分层 Tab 补全发现并执行 `/alda play`；
4. 提出可听辨的修改，保存新版本并试听；
5. 查看 `/project` 和 `/project versions`，使用 `/project switch` 切换旧版本，再用 `/alda export`
   导出 Alda 与 MIDI；
6. 在一次长操作中按 Ctrl+C，确认回到提示符且原有效版本仍可播放；
7. 临时使模型配置无效，重新打开项目，仍能播放、恢复和导出已有版本；
8. 从打开项目到退出的整个过程中，确认输入编辑自然、当前阶段清楚、常用操作易发现，并且错误后知道
   如何继续。

自动化验收证明状态和不变量，真实终端验收判断人体工程学；两者都通过后，本迭代才能关闭。
