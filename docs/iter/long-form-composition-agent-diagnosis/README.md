# 长篇叙事作曲 Agent：两次运行的困境、改进与判断边界

## 目的与范围

本文记录同一五分钟叙事配乐任务在结构化曲式机制落地前后的两次真实运行，作为后续优化长篇作曲 Agent
及评估按需 subagent 委派的工程基线。

运行任务：依据《香樟太守》创作约五分钟、具有东方 Project 风格的叙事主题曲。

本文分析对象仅限于终端中公开显示的模型说明、工具往返记录与宿主校验结果，不将其等同于模型不可见的内部推理过程。

证据分为三类：

- **宿主事实**：最终统计与校验结果，可直接复核。
- **可见陈述**：模型公开输出的计划、诊断与中间测量，用于说明其采用过的策略。
- **分析推断**：基于事实与陈述提出的工程解释，仍需更多案例验证。

这是同一题目的纵向案例研究，能比较工程机制带来的行为变化，但仍不能替代跨题目对照或人工音乐评价。

## 证据

### E1：时长主要依赖多轮扩展收敛

中间日志出现：

```text
36 秒 → 81 秒 → 102 秒 → 179 秒 → 281.9 秒 → 248 秒 → 265 秒 → 287.8 秒
```

随后模型主要通过增加主题与低音循环次数进行修正，例如：

- `group_a * 36`
- `group_a * 41`
- `group_low * 48`

说明时长误差长期主导搜索方向。达到 281.9 秒后，为修复尾部织体又回退到 248 秒和 265 秒，表明过程并非
单调逼近，而是在总时长、声部结尾和配器之间振荡；修复一个维度会破坏另一个维度。

### E2：诊断快速收缩为“增加循环”

模型公开写道：

```text
每个声音出现太少，应增加反复。
东方 Project 风格依赖密集 loop。
```

然而时长不足仍可能来自：

- 缺少独立段落；
- 乐句长度不足；
- 段落职责缺失；
- 声部提前结束。

日志没有逐项比较，而是优先提高循环次数，因此属于诊断空间过早收缩。

### E3：独立声部时间轴多次误判

日志中模型不断修正自己的理解：

```text
所有声部从各自 0 秒开始。
同一乐器再次出现会继续累计时间。
Trumpet 第二段并非结尾，而是紧接上一段。
```

最终不得不加入长休止，将号角延迟至结尾。

问题本质不是语法，而是声部时间模型不稳定。

### E4：总时长达标后暴露尾部织体问题

候选达到 281.9 秒后又发现：

```text
Harpsichord 到 281.9 s
Flute 仅到 228 s
最后约 54 s 几乎只有 Harpsichord
```

这是一次有效的结构诊断：关注点从总时长提升到各声部结束分布与尾部织体。

最终尾差缩小至 1.8 秒。

### E5：整体重构多于局部修补

公开记录中反复出现：

```text
重新设计整个作品
重新写所有声部
重构完整版本
直接写最终版
```

同一次运行不断改变：

- 段落数量
- 核心主题
- 配器结构
- 声部进入策略

说明缺乏稳定的局部修改单元。

### E6：规划循环与动作延迟

模型多次表示：

> 现在开始写最终版本。

随后继续输出新的规划与换算，而没有立即进入工具调用。

表现为规划能够持续扩展，但较难及时收敛到一次有限修改。

### E7：协议错误仍消耗预算

日志包含两类无价值往返：

- 乐器名修正（`midi-cellobass → midi-contrabass`）
- 正式提交遗漏 `alda_code`

虽然最终恢复成功，但额外增加了一轮模型调用与工具交互。

最终 `work.alda` 只有 1,695 字节，明显低于候选预检的 32 KiB 和工具参数的 64 KiB 上限，因此遗漏
`alda_code` 不能归因于本次源码实际超限。模型虽然多次担心 16 KiB 预算并主动用变量、反复压缩，但该约束
在最终产物上没有成为真实瓶颈。

### E8：缺少段落级时间反馈

当前 `inspect_alda_source(scope=candidate)` 能返回：

- 总时长
- 声部结束时间
- 事件数
- 全局时间线

但无法返回：

- `%marker` 实际秒数；
- 各声部在 Marker 区间内的覆盖情况。

因此只能知道：

> Flute 于 228 秒结束。

却无法直接验证：

> 竹潭段是否真正位于 180–220 秒。

### E9：缺少作品表达反馈

自动循环目前只有静态指标：

- 时长
- Peak
- RMS
- 静音检测

缺少对于以下内容的反馈：

- 主题发展
- 和声组织
- 风格接近程度
- 叙事峰值
- 结尾完整度

因此模型自然优先优化可测量指标，而非作品表达本身。

### E10：自然语言计划与最终产物脱节

模型多次声称作品包含引子、敕令、主题、竹潭、女王和凯旋等可定位段落，最终宿主事实却是：

```text
标记：0 个定义，0 个引用
```

源码中的 `# ===== 叙事插段 =====` 等注释只描述作者意图；Alda 各声部拥有独立时间线，源码排列顺序不能
证明这些片段在听觉时间上形成了同一段落。没有 Marker 就无法验证模型公开说明中的段落位置。

最终说明还列出圆号和英国管，但真实解析出的 10 个声部不包含二者。说明文本保留了早期规划中的配器，
没有严格从最终源码和解析结果重建。这是计划、自我描述与实际 Artifact 状态漂移的直接证据。

### E11：最终源码确实由少量材料高倍率展开

最终 `work.alda` 只有 43 行、1,695 字节，SHA-256 为
`347fca473b9381a75ab69673ef275da581102ce6a876f9ecad0d765ff69ca294`，主要展开点是：

关联的文档快照仅规范化补充了文件末尾换行，其他字节与原稿一致；快照 SHA-256 为
`eb232aca0f0a78724a4ac625be83b0145ebfdbe8cba57a214ab061d6b94cabc9`。

```text
[group_a] * 45
[group_low] * 48
[group_b] * 36
```

叙事特色声部主要通过 `r1 * N` 延迟后重复 2–3 次短动机进入。4024 个可播放事件因此不能单独证明材料
丰富；它们多数由少量变量和高倍率反复展开。最终作品是否机械仍需试听，源码事实只能证明模型确实采用了
这种生成策略。

### E12：预检候选不能直接成为正式提交

当前 `CandidateCheckpoint` 已在 Agent 内保存预检通过的 `alda_code` 与检查结果，但没有可供模型引用的稳定
ID；`submit_result(kind=candidate)` 仍要求再次发送完整 `alda_code`。本次模型在完成预检后首次正式提交遗漏
该字段，产生一次协议恢复。

这不是源码大小导致的错误，但说明预检事实与正式提交之间存在重复传输和重复协议责任。已经检查的候选应
能由内容哈希引用提交，避免模型重新组装同一份大参数。

### E13：结构机制落地后调用成本反而上升

第二次运行最终成功，但用了 20 次模型调用、19 次工具往返和 3 次协议恢复，均高于第一次的 14、13、1。
这不能证明 Marker、form_plan 或 checkpoint 无效；它说明这些机制虽然增加了可验证事实，却没有自动减少模型在
作曲设计、拍数换算、Alda 语法和协议字段之间切换的成本。

### E14：完整创作意图被误判为只需计划

用户直接要求“为该故事铺主题曲”，第一次回复却以 `kind=plan` 结束，用户必须再输入“继续”才进入创作。
当前 `requests_complete_candidate()` 没有稳定识别这一表述。结构计划本应是同一创作回合内的内部产物，不能
因为引入 form_plan 就额外制造一次用户批准门。

### E15：form_plan 仍是事后回填，而非稳定作曲契约

公开轨迹中的计划依次经历：

```text
420 s 草案 → 压缩为 300 s → 实际 406 s → 291 s → 最终登记为 297.14 s
```

Marker 与最终 form_plan 的确对齐，但计划时间跟随源码和手算错误反复变化。当前字段只约束段落 ID、时间、职责、
材料动作和能量，尚未固定精确动机、和声区域、织体或主题变形关系，因此更接近成品结构登记，而非可供实现者
执行和审查的作曲契约。

### E16：Marker 对齐仍可隐藏短句高倍率展开

第二次源码的主要材料仍是：

```alda
@section_a melA16*7
@section_b phraseB*14
@section_c phraseC*12
@section_d phraseD*8
@section_a2 melA16*8

@section_a arpA*28
@section_a2 arpA*32
```

A 与 A2 的长笛材料几乎相同，钢琴在多数段落重复同一个 `arpA`。7 个 Marker 和 3101 个事件证明结构边界
存在、事件可播放，却不能证明段落内部存在充分发展。

### E17：拍数误判造成跨段溢出和同声部重叠

模型公开换算多次把变量名或音符数量当成拍数。源码实际为：

```text
phrase1  = 4 拍
phrase2  = 3.5 拍
melA16   = 7.5 拍，并非 16 拍
arpA     = 3.5 拍，并非 4 拍
trem     = 4 拍，并非 8 拍
phraseD  = 15 拍，并非 12 拍
```

D 段预算为 96 拍，但 `phraseD*8` 实际为 120 拍，长笛最后 24 拍越过 A2 Marker；随后
`@section_a2` 又把该声部游标跳回段首，形成同声部时间重叠。事件证据中 D 段长笛有 32 个 onset，A2 段有
128 个，其中包含从 D 段泄漏的 8 个 onset。现有 Marker 检查只证明边界存在，尚未拒绝跨段溢出、游标向后跳
或意外同声部重叠。

### E18：音乐说明与最终源码仍不一致

模型最终声称使用都节音阶、半音关系和转调发展，但候选源码没有升降音、调号或可定位的调性迁移。该说明不是
从最终 Artifact 重建的事实。类似地，事件数量和配器数量也不能替代对音高、和声与主题变形的源码核对。

### E19：checkpoint 有效，但协议仍过于脆弱

第二次运行最终能用 `candidate_ref.source_hash` 提交，证明 checkpoint 引用方向有效；但此前又发生三类低价值
恢复：并行工具调用被整体拒绝、候选尚未成为 work/current 时调用 `render_score current`、提交时两次携带
与 `candidate_ref` 冗余的 `alda_code` 或 `form_plan`。一致的冗余字段应由宿主安全归一化，或在 schema 和错误
提示中直接阻止模型形成错误组合。

本次只验证了初次完整创作。`edit_scope`、受限 patch 和 Marker 局部播放虽然已有实现与自动化测试，尚未在
真实长曲修改中完成端到端验收。

## 当前困境

```text
技术闭环稳定
├── Alda 解析
├── 时长约束
├── 候选检查点
├── MIDI / WAV 渲染
└── 运行统计

长篇创作仍不稳定
├── 总时长压倒结构设计
├── 多目标修正来回振荡
├── Marker 已可定位，但不约束段内音乐内容
├── 拍数误判可造成跨段溢出和游标回跳
├── 计划说明与最终产物脱节
├── 整体重写多于局部修改
├── 作曲设计与 DSL 排错争夺同一上下文
├── 风格退化为表面循环
└── 静态成功无法代表作品质量
```

因此当前更值得投入的是纵向提升生成链，而不是继续扩展风格或乐器种类。

## 根因判断

### 1. 反馈目标不对称

可测量：

- 时长
- 语法
- 乐器
- 声部结束时间

不可自动测量：

- 主题发展
- 叙事对应
- 风格一致程度

搜索自然偏向代理指标。

### 2. 时间表示已建立，但契约表达不足

Marker 和 form_plan 已建立自然语言段落与 Alda 时间轴的统一映射，但当前契约没有精确动机、和声路线、织体、
变形关系和声部游标边界。模型仍需同时承担艺术设计、拍数换算和 DSL 排错，计划容易退化为事后登记。

### 3. 缺少持久修改契约

系统能恢复源码，却不能恢复：

- 哪些段落已稳定；
- 本轮只修改哪些部分；
- 哪些指标必须保持。

导致工具反馈容易触发全局重规划。

### 4. 风格抽象过度

模型识别了：

- 高速旋律
- 对位
- Loop
- 游戏音乐结构

却将主题再现进一步简化为高次数重复，而缺乏持续变形与发展。

### 5. 预检与提交协议重复

候选预检已经保存完整源码与检查结果，正式提交却不能引用该事实，仍要求模型重新发送同一源码。这增加了
无价值的参数组装责任，并使最后一步可能因缺字段或截断失败。

### 6. 基础错误预防不足

乐器名与协议错误不是主要问题，但持续增加无价值交互成本。

本案例中最终源码远未达到字节上限，不能把高倍率循环归因于真实传输容量不足。更准确的解释是：模型将
源码预算提前当成设计约束，并选择了同时最容易压缩源码和扩展时长的表达方式。

## 与正常作曲流程的比较

围绕固定时长创作本身完全正常。

真正缺失的是 **Spotting Sheet / Tempo Map** 对叙事时间点的稳定映射。

正常流程通常具有：

| 正常流程 | 当前 Agent |
|---|---|
| 明确情节时间点 | 仅掌握总时长 |
| 主题不断变形 | 提高循环次数 |
| 谱面 + 听觉共同判断 | 静态指标主导 |
| 局部修改 | 频繁整体重构 |

因此问题不是“考虑时长”，而是缺少稳定的中间结构表示。

---

## 不能推出的结论

本案例不能证明：

- 最终作品必然机械或难听；
- 事件数代表质量；
- subagent 已经提高了作品质量或降低了成本；
- 所有声部必须等长；
- 东方 Project 风格等于 Loop。

这些结论仍需试听与源码分析支持。但第二次运行已经提供了启动按需委派 A/B 的证据：用对照实验验证职责
隔离是否有收益，而不是直接建设固定角色或通用 Multi-Agent 平台。

---

## 建议的优化顺序

### P0：补齐 Marker 时间与游标安全证据

- 保留已实现的 Marker 时间、段落事件和声部覆盖；
- 检测声部越过下一 Marker、`@section` 向后跳和同声部意外重叠；
- 将精确拍数交给解析结果，不再依赖模型按源码手算。

### P1：稳定长曲工作流

- 先建立段落骨架；
- 再增加特色配器；
- 每轮仅修改 1–2 个区段；
- 保持已稳定段落不被重写。

局部修改优先基于最新工作稿或候选 checkpoint 发送受限 patch；全量源码只用于初次创作或用户明确要求的
整体重写。无论采用 patch 还是全量源码，都由同一套段落保持检查判断结果。

### P2：建立作品表达评估

完整作品试听为默认路径；出现具体问题时，再按 Marker 或时间位置播放带前后文的局部窗口。以下 Rubric
只作为可选提示，不要求逐段评分或确认：

- 主题生命周期
- 段落辨识度
- 叙事峰值形成
- 重复与变形
- 结尾完整度

静态指标与试听结论应分别保存。

### P3：减少低价值交互

- 乐器名自动建议；
- 检测未修改候选；
- 为预检候选返回内容哈希，正式提交直接引用该 checkpoint；
- 统一数值显示格式。

### P4：验证按需委派

以不委派的 Composer 运行作为基线，允许 Composer 自行选择边界清晰的音乐设计、Alda 实现或只读复核任务，
通过 `task/context` 交给隔离 subagent。subagent 不继承主对话或乐谱源码，但可查询文档、检查临时片段，并在
项目会话中只读检查 work/current；返回文本仍由 Composer 判断和整合，现有宿主继续负责最终检查和提交。
是否保留该能力由总模型调用、DSL 错误、主题可定位性和完整试听 A/B 决定，不预设 Worker、段落家族、
Reviewer 或 Workflow。

## 阶段验收基线

连续代表性任务满足：

- 长曲 4–6 次调用完成；
- 协议恢复为 0；
- 预检通过后的正式提交不再重传 `alda_code`；
- Marker 可定位所有计划段；
- 时长修正不再主要依赖循环放大；
- 人工试听能够辨认主题、叙事峰值与完整结尾。

达到以上条件后，再考虑横向扩展风格能力。

## 工程处置结果（2026-08-18）

本案例形成的工程方案已经落地：

- Marker 检查从全曲位置扩展为段落边界、事件、声部覆盖和稳定事件哈希；
- 120 秒以上候选必须提供与 `%section_<id>` 对齐的 4–10 段 `form_plan`，并随工作稿、恢复候选和版本持久化；
- 预检通过后可用 `candidate_ref.source_hash` 正式提交，不再重传完整源码；
- 修改结构化乐谱必须声明 `edit_scope`，局部模式机械保护非目标段落；
- `inspect_alda_patch` 可在已知 source hash 上检查少量唯一替换，不直接改写项目；
- 整曲试听和完整 WAV 仍是默认路径；按 Marker 的带上下文局部播放只用于定位问题和 A/B，不进行逐段审批。
- `delegate` 已提供带最小只读工具集的隔离 subagent 循环，所有内部调用计入总模型调用并单独统计委派数。

这些机制解决的是状态漂移、全局重写和反馈粒度，不自动判断主题发展或风格质量。下一步先补齐游标回跳、
跨段溢出和意外重叠检查，再用新的 3–5 分钟任务对照不委派与按需委派的调用成本和完整试听结果；
不能用机制完成替代音乐质量验收，也不能在 A/B 前宣称 subagent 有效。
