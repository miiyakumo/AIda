# 长篇叙事作曲 Agent：当前困境、证据与判断边界

## 目的与范围

本文记录一次真实的五分钟叙事配乐运行案例，作为后续优化长篇作曲 Agent 的工程基线。

运行任务：依据《香樟太守》创作约五分钟、具有东方 Project 风格的叙事主题曲。

本文分析对象仅限于终端中公开显示的模型说明、工具往返记录与宿主校验结果，不将其等同于模型不可见的内部推理过程。

证据分为三类：

- **宿主事实**：最终统计与校验结果，可直接复核。
- **可见陈述**：模型公开输出的计划、诊断与中间测量，用于说明其采用过的策略。
- **分析推断**：基于事实与陈述提出的工程解释，仍需更多案例验证。

这是一次案例研究，不能单独证明长篇创作能力，也不能仅凭静态指标评价作品质量。

最终候选成功完成完整技术闭环。

## 证据

### E1：时长主要依赖多轮扩展收敛

中间日志连续出现：

```text
36 秒 → 81 秒 → 102 秒 → 179 秒 → 281.9 秒
```

随后模型主要通过增加主题与低音循环次数进行修正，例如：

- `group_a * 36`
- `group_a * 41`
- `group_low * 48`

说明时长误差长期主导搜索方向。

### E2：诊断快速收缩为“增加循环”

模型公开写道：

```text
每个声音出现太少，应增加反复。
东方 Project 风格依赖密集 loop。
```

然而时长不足仍可能来自：

- 缺少独立段落；
- 乐句长度不足；
- 段落职责缺失；
- 声部提前结束。

日志没有逐项比较，而是优先提高循环次数，因此属于诊断空间过早收缩。

### E3：独立声部时间轴多次误判

日志中模型不断修正自己的理解：

```text
所有声部从各自 0 秒开始。
同一乐器再次出现会继续累计时间。
Trumpet 第二段并非结尾，而是紧接上一段。
```

最终不得不加入长休止，将号角延迟至结尾。

问题本质不是语法，而是声部时间模型不稳定。

### E4：总时长达标后暴露尾部织体问题

候选达到 281.9 秒后又发现：

```text
Harpsichord 到 281.9 s
Flute 仅到 228 s
最后约 54 s 几乎只有 Harpsichord
```

这是一次有效的结构诊断：关注点从总时长提升到各声部结束分布与尾部织体。

最终尾差缩小至 1.8 秒。

### E5：整体重构多于局部修补

公开记录中反复出现：

```text
重新设计整个作品
重新写所有声部
重构完整版本
直接写最终版
```

同一次运行不断改变：

- 段落数量
- 核心主题
- 配器结构
- 声部进入策略

说明缺乏稳定的局部修改单元。

### E6：规划循环与动作延迟

模型多次表示：

> 现在开始写最终版本。

随后继续输出新的规划与换算，而没有立即进入工具调用。

表现为规划能够持续扩展，但较难及时收敛到一次有限修改。

### E7：协议错误仍消耗预算

日志包含两类无价值往返：

- 乐器名修正（`midi-cellobass → midi-contrabass`）
- 正式提交遗漏 `alda_code`

虽然最终恢复成功，但额外增加了一轮模型调用与工具交互。

### E8：缺少段落级时间反馈

当前 `inspect_alda_source(scope=candidate)` 能返回：

- 总时长
- 声部结束时间
- 事件数
- 全局时间线

但无法返回：

- `%marker` 实际秒数；
- 各声部在 Marker 区间内的覆盖情况。

因此只能知道：

> Flute 于 228 秒结束。

却无法直接验证：

> 竹潭段是否真正位于 180–220 秒。

### E9：缺少作品表达反馈

自动循环目前只有静态指标：

- 时长
- Peak
- RMS
- 静音检测

缺少对于以下内容的反馈：

- 主题发展
- 和声组织
- 风格接近程度
- 叙事峰值
- 结尾完整度

因此模型自然优先优化可测量指标，而非作品表达本身。

## 当前困境

```text
技术闭环稳定
├── Alda 解析
├── 时长约束
├── 候选检查点
├── MIDI / WAV 渲染
└── 运行统计

长篇创作仍不稳定
├── 总时长压倒结构设计
├── 声部时间轴容易漂移
├── 缺少 Marker 实际位置
├── 整体重写多于局部修改
├── 风格退化为表面循环
└── 静态成功无法代表作品质量
```

因此当前更值得投入的是纵向提升生成链，而不是继续扩展风格或乐器种类。

---

## 根因判断

### 1. 反馈目标不对称

可测量：

- 时长
- 语法
- 乐器
- 声部结束时间

不可自动测量：

- 主题发展
- 叙事对应
- 风格一致程度

搜索自然偏向代理指标。

### 2. 缺少统一时间表示

自然语言段落计划与 Alda 声部之间缺少统一映射，因此 Marker 无法成为可验证对象。

### 3. 缺少持久修改契约

系统能恢复源码，却不能恢复：

- 哪些段落已稳定；
- 本轮只修改哪些部分；
- 哪些指标必须保持。

导致工具反馈容易触发全局重规划。

### 4. 风格抽象过度

模型识别了：

- 高速旋律
- 对位
- Loop
- 游戏音乐结构

却将主题再现进一步简化为高次数重复，而缺乏持续变形与发展。

### 5. 基础错误预防不足

乐器名与协议错误不是主要问题，但持续增加无价值交互成本。

---

## 与正常作曲流程的比较

围绕固定时长创作本身完全正常。

真正缺失的是 **Spotting Sheet / Tempo Map** 对叙事时间点的稳定映射。

正常流程通常具有：

| 正常流程 | 当前 Agent |
|---|---|
| 明确情节时间点 | 仅掌握总时长 |
| 主题不断变形 | 提高循环次数 |
| 谱面 + 听觉共同判断 | 静态指标主导 |
| 局部修改 | 频繁整体重构 |

因此问题不是“考虑时长”，而是缺少稳定的中间结构表示。

---

## 不能推出的结论

本案例不能证明：

- 最终作品必然机械或难听；
- 事件数代表质量；
- 必须引入多 Agent；
- 所有声部必须等长；
- 东方 Project 风格等于 Loop。

这些结论仍需试听与源码分析支持。

---

## 建议的优化顺序

### P0：补齐 Marker 时间证据

- 返回 `%marker` 实际秒数；
- 返回各声部 Marker 覆盖；
- 支持计划时间与实际时间直接比较。

### P1：稳定长曲工作流

- 先建立段落骨架；
- 再增加特色配器；
- 每轮仅修改 1–2 个区段；
- 保持已稳定段落不被重写。

### P2：建立作品表达评估

人工试听 Rubric 建议包含：

- 主题生命周期
- 段落辨识度
- 叙事峰值形成
- 重复与变形
- 结尾完整度

静态指标与试听结论应分别保存。

### P3：减少低价值交互

- 乐器名自动建议；
- 检测未修改候选；
- 提交前检查 `alda_code`；
- 统一数值显示格式。

---

## 阶段验收基线

连续代表性任务满足：

- 长曲 4–6 次调用完成；
- 协议恢复为 0；
- Marker 可定位所有计划段；
- 时长修正不再主要依赖循环放大；
- 人工试听能够辨认主题、叙事峰值与完整结尾。

达到以上条件后，再考虑横向扩展风格能力。
