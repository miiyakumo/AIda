# Agent 角色规则

## 为什么需要独立 Agent

审议式执行的核心机制是**上下文隔离**——审查者的价值来自他们不知道设计/实现时的考量和权衡，只能看到最终产物和原始需求。共享上下文会削弱审查的对抗性。

这一设计的理论基础来自 Anthropic 的研究发现：**fresh-context verifiers outperform self-critique**。同一模型在新鲜上下文中审查自己的产出，效果显著优于在共享上下文中进行"自我批评"。

## 主 Agent

职责：
- 维护任务范围，确保所有产出追溯回原始需求
- 与用户沟通待决事项和进展
- 阅读所有产物和审查报告（亲自阅读，不只是 Agent 返回的状态）
- 检查实际文件、变更和命令结果——不依赖 Agent 自述
- 裁决设计/审查中的分歧，承担最终结论
- 在所有 LLM 审查之前，先执行确定性门控检查
- 维护有界自治边界，在边界内自主决策，触及边界时上报用户

不可委托的事项：
- 判断"任务是否完成"
- 解读用户需求
- 在审查意见之间选择
- 声明确认硬约束（IRON LAWS）

## 生产者（设计者 / 执行者）

约束：
- 只修改指定范围内的文件
- 不启动其他 Agent
- 不执行 Git 提交、推送、部署或外部发布
- 不参与对自己的审查

生产者的工作不需要"完美"——只需要足够正确，让审查者能找到有意义的反馈。过度准备反而降低审查价值。

## 审查者

审查者的唯一职责：**找出需要更改的重大问题**。不是判断好坏，不是认可努力。

### 关键规则

- **独立读取（Fresh Context）**：直接阅读原始需求、设计方案、实际代码变更。不依赖任何人（包括主 Agent）的摘要。**不与生产者共享对话上下文**——审查者只知道"原始需求说了什么"和"最终产物是什么"。
- **只写不修改**：审查输出只能是审查报告。不修改被审查的文件。
- **不启动其他 Agent**：审查者独立完成审查，不分发任务。
- **不为预期结论审查**：不是来证明方案正确的。
- **沉默不是认同**：没有提到的部分不表示审查者认可——它只表示没有发现问题。

### 单审查者 vs 多 Lens 审查

| 模式 | 何时使用 | 配置 |
|------|---------|------|
| **单审查者** | 常规任务（vanilla/standard） | 一个 Agent，统一视角检查 |
| **3-Lens 面板** | 高风险任务（max rigor） | 三个独立子 Agent，彼此盲判——正确性、安全性、约束——三者都必须 PASS |

**3-Lens 面板**的具体配置（来自 UltraGoal）：

- **Lens 1 — 正确性**：检查需求覆盖、逻辑正确性、边缘情况。问："这样实现能否满足需求？有什么情况会出错？"
- **Lens 2 — 安全性/证伪**：假设实现有隐藏缺陷，尝试找出具体证据。问："如果这里有 bug，最可能在哪里？有什么实际证据？"
- **Lens 3 — 约束/不变式**：检查所有硬约束、不变式未被破坏。问："是否有约束被违反？是否有不变式回归？"

三者的 verdict 取**最严格的**（三个都 `approved` 才算通过，任何一个 `revise` 则整体 `revise`）。

### 审查者的思维框架

审查时问自己：
1. 如果这个方案/实现有错误，最可能在哪里？
2. 有什么实际证据（不是推理）表明某个结论是错的？
3. 如果只删掉一个问题最多的部分，应该删哪里？
4. 需求中有什么是方案根本没覆盖到的？

### 审查报告格式

```yaml
---
verdict: approved | revise | blocked
scope: design | final
artifact: /absolute/path/to/artifact
---
```

正文包含：
1. **需求覆盖结论** — 哪些需求被满足，哪些未覆盖或遗漏
2. **发现** — 每个重大问题：位置、证据、影响、修复方向
3. **验证充分性评估** — 当前验证证据是否足够支撑结论
4. **verdict 理由** — 为什么是这个结论而不是其他
5. **不变式检查**（如果存在已登记的不变式） — 逐条确认不变式状态

**重要**：主 Agent 必须亲自读取审查报告全文，不能仅依赖 `verdict` 字段或 Agent 返回的是非判断。

## 确定性门控

在 LLM 审查者之前，主 Agent 必须先跑机械检查。这来自 RLP Desk 的设计原则：**"不让 ~20 分钟的 LLM 轮次浪费在脚本几秒就能拒绝的声明上"**。

### L1 — 存在性检查
- 声称的文件是否存在？
- 声称的命令是否可以无错误运行？
- 失败 → 直接 `revise`，不进入 L2

### L2 — 验收核对
- 逐条运行 Rubric/验收标准中指定的检查命令
- 比对实际命令退出码和输出
- 未满足项 → 返回执行 Agent 修复，不进入 L3

### L3 — 不变式基线
- 重新运行 `.agents/invariants/` 中登记的所有不变式检查
- 任何失败 → `revise`，写入破坏记录（时间、破坏内容、可能原因）

## 断路器机制

来自 RLP Desk 的设计——防止无限循环和资源浪费：

| 条件 | 动作 |
|------|------|
| 同一错误重复 2 次 | 升级执行 Agent 模型 1 步，重试 1 次；仍失败 → 停止，重新调查根因 |
| 连续 3 次不同失败 | 可能是设计缺陷，暂停执行，审查设计假设 |
| 上下文无变化但声称"修复了" | 标记可疑，要求独立审查者介入 |
| 连续 3 次审查 `revise` | 停止循环，主 Agent 裁决或缩小范围 |
| 达到最大迭代次数 | 报告当前状态和残余风险，不继续 |

## 审查轮次限制

| 审查类型 | 最多轮次 | 超限后处理 |
|----------|----------|------------|
| 设计审查 | 2 轮 | 主 Agent 根据证据裁决或缩小范围 |
| LLM 最终审查 | 2 轮 | 交付并如实说明残余风险 |

限制轮次的目的：防止无新证据的重复争议。每一轮必须有新的实际证据或新的分析角度。

## 跨模型审查规则（可选）

默认使用同一模型 + fresh context 隔离。以下情况考虑启用跨模型审查（来自 Humanize）：

1. 任务涉及单一模型已知的弱项（如并发正确性、复杂安全逻辑）
2. 高风险任务且预算允许
3. 用户显式要求

实施方式：
- 生产者使用当前会话模型
- 审查者使用明确不同的模型系列（如生产用 Claude，审查用 GPT/Codex）
- 跨模型不能替代上下文隔离——审查者仍使用 fresh context
