# 审议式执行

以"需求—设计—执行—验证—复核"的闭环完成复杂任务。不提供步骤清单——Agent 应根据任务自行判断每个环节的深度和形式。

**核心架构**：主 Agent 是循环编排者（Leader），每个执行 Agent（Worker）完成后的声明不可信任——必须通过门控和独立验证器（Verifier）才能放行。验证失败 → 问题注入下一轮执行 → 重新执行，直到门控释放。

```
BRIEF → DESIGN → EXECUTE → DONE CLAIM → GATE → VERIFY → PASS → RELEASE
                       ↑                           ↓
                       └── FEEDBACK (fix contract) ←── FAIL
```

这个循环不是可选的——它是对"宣称完成"的自动响应机制。

## 核心信念

审议式执行基于三条信念，所有规则是它们的推论：

1. **证据高于叙事** — Agent 的自述不是验证；实际文件、命令结果、渲染输出才是。判断任何产物的正确性之前，先看实际产物。
2. **审查是对抗而非确认** — 审查者的职责是证伪，不是背书。审查者从新鲜上下文独立读取原材料，不与生产者共享推理链条。
3. **范围的唯一裁判是原始需求** — 一切产出追溯到用户最初的要求。没有需求覆盖的修改是越界。

这三条信念意味着：做最小充分的工作，每次修改后有实际证据支撑，审查者独立质疑一切关键结论。

## 流程选择

根据任务复杂度选择最小充分流程：

| 流程 | 适用场景 |
|------|----------|
| **轻量** | 小修改、简单查询——微设计→实施→自检→交付 |
| **仅设计** | 只需要方案不需要实施——调查→设计→审查→交付方案 |
| **执行已有设计** | 已有审批过的设计——校验设计→增量执行→自验证 |
| **设计并执行** | 完整任务，方案和执行都有风险——全流程（含门控和断路器） |

选择原则：**为任务匹配流程，不让任务适应流程**。不确定时选更充分的流程。

## 流程骨架

### 1. 明确任务

区分四类信息：
- **明确要求** — 用户说了什么（不可省略）
- **合理推断** — 从上下文可推导（应标注为推断）
- **待决事项** — 需要用户决策（只在显著改变范围、安全、兼容性或不可逆操作时才问）
- **明确排除** — 用户说不要什么（防止范围蔓延）

### 2. 有界自治

从 Ouro Loop 借鉴：在任务启动时声明以下边界，并写入状态文件供验证阶段比对。

- **危险区（DANGER ZONES）** — 哪些文件/系统/操作需要额外谨慎
- **绝不操作（NEVER DO）** — 绝对禁止的动作（如 `git push -f`、删除数据库）
- **硬约束（IRON LAWS）** — 不可违背的规则（如"必须向后兼容""所有 API 必须有测试"）

边界不是限制——它们让 Agent 在边界内自由行动而不需要每步确认。

### 3. 调查现状

获取一手证据——阅读实际文件，运行实际命令，确认实际行为。调查深度与任务风险成正比。

**设计之前必须先看清现状。** 对现状的假设错误是大多数方案失败的根源。

### 4. 设计与审查

设计说明：问题、约束、方案、边界、异常路径、验证方法。讨论兼容性、迁移、安全、性能等仅在任务需要时。

**非轻量任务应进行独立设计审查。** 审查者从新鲜上下文独立读取需求和设计，不参与设计过程。

审查结论：
- `approved` — 可继续
- `revise` — 有证据支持的重大问题，应修订
- `blocked` — 缺用户决策或外部条件

最多两轮设计审查。第二轮仍有重大问题时，主 Agent 根据证据裁决或缩小范围。

### 5. 增量执行

- 拆成顺序明确、可独立验证的最小切片
- 一次完成一个切片，完成后以实际产物验证
- 设计假设被事实否定时，暂停并修订设计

**同一失败处理（断路器机制）**：
| 条件 | 动作 |
|------|------|
| 同一错误重复 2 次 | 升级模型重试 1 次，仍失败则停止并重新调查根因 |
| 连续 3 次不同失败 | 架构升级——可能是设计问题，暂停执行并审查设计假设 |
| 上下文无变化但声称"修复了" | 标记可疑，要求独立审查者介入 |

**主 Agent 必须亲自检查每个切片的实际产物**，不能依赖执行 Agent 的自述。

### 6. 验证与门控

验证分两层：**确定性门控**（即时，不用 LLM）和 **LLM 审查**（用新鲜上下文，最多两轮）。

#### Done-Claim Hook：执行 Agent 完成后自动触发

执行 Agent 宣称"完成"时，以下流程**自动触发且不可跳过**（来自 Humanize 和 UltraGoal 的设计）：

```
执行 Agent → 宣称 DONE
              │
              ▼
        ┌── GATE ──┐
        │ L1 存在性  │── FAIL ──→ 拒绝声明，fix contract 返回执行 Agent
        │ L2 验收核对│── FAIL ──→ 拒绝声明，fix contract 返回执行 Agent  
        │ L3 不变式  │── FAIL ──→ revise，破坏记录写入
        └──────────┘
              │ ALL PASS
              ▼
        ┌─ VERIFY ──┐
        │ LLM 审查者 │── FAIL ──→ 提取问题，fix contract 注入下一轮 Worker prompt
        │(fresh ctx) │           → 断路器计数 +1，可能升级模型
        └──────────┘
              │ PASS
              ▼
           RELEASE ──→ 继续下一个切片
```

**关键规则**：
- 声明完成不等于完成——**没有门控通过的 DONE 不构成任何保证**
- 门控必须在每个执行 Agent 完成声明后触发，主 Agent 不得省略或手动"判断应该没问题"
- 门控失败时，必须向执行 Agent 返回**修复契约（fix contract）**——具体指出什么检查失败、实际证据是什么，不是模糊地说"再检查一下"
- 断路器跟踪重复失败，达到上限后不再循环，改为上报用户
- 最终 RELEASE 后，通过的验收条件可提取为不变式写入 `.agents/invariants/`

##### 门控安全机制（来自 UltraGoal 和 RLP Desk）

门控必须是**可靠的**——不能因门控本身的故障而卡死 session：

| 机制 | 规则 |
|------|------|
| **Fail Open** | 门控脚本自身出错时**释放循环**，不 trapped session。错误记录写入日志但不阻止继续 |
| **Turn 预算** | 默认 25 个执行轮次，达到上限时门控要求诚实状态报告，被忽略则自动暂停当前目标 |
| **紧急停止** | 用户随时说"停止"可直接释放门控，不计入断路器 |
| **Session 绑定** | 门控绑定到装弹 session；同一 repo 的其他 session 不受影响（来自 UltraGoal） |
| **空循环检测** | 门控连续 3 次触发但上下文无实质变化 → 暂停，警告用户可能存在循环死锁 |

#### 确定性门控（LLM 审查之前先行）

在调用任何 LLM 审查者之前，先跑机械检查。任何一层失败都不进入下一层：

| 层 | 检查内容 | 失败处理 |
|----|---------|---------|
| **L1 — 存在性** | 声称的文件是否存在，声称的命令是否可运行 | 直接拒绝完成声明，不调用 LLM |
| **L2 — 一致性** | Ruby/验收标准逐条比对实际产物（运行实际命令获取结果） | 标记未满足项，返回执行 Agent 修复 |
| **L3 — 基线** | 已有不变式（invariants）是否仍然通过 | 任何失败 → `revise`，写入破坏记录 |

**门控原则**：能用脚本验证的绝不用 LLM——"不让 ~20 分钟的 LLM 轮次浪费在脚本几秒就能拒绝的声明上"（RLP Desk）。

#### LLM 独立审查

确定性门控全部通过后，启动独立验证者。详见 [reference/agent-rules.md](reference/agent-rules.md)。

验证手段按证据强度排序：
1. 自动化测试、构建、静态检查（最强）
2. 实际运行示例、数据对比
3. 手工检查、逐条验收核对（最弱但仍有价值）

#### Fresh Context 隔离

生产者和审查者不共享上下文——审查者的价值来自不知道实现时的考量和权衡，只能看到最终产物和原始需求。这是从 UltraGoal 和 Anthropic 研究得出的核心设计原理：**"fresh-context verifiers outperform self-critique"。**

### 7. 最终复核

执行完成后，由**新任独立审查者**检查原始需求、设计、实际产物、验证证据。最多两轮。

## 审查标准

### 审查者思维框架

审查时问自己（来自当前 skill）：
1. 如果这个方案/实现有错误，最可能在哪里？
2. 有什么实际证据（不是推理）表明某个结论是错的？
3. 如果只删掉一个问题最多的部分，应该删哪里？
4. 需求中有什么是方案根本没覆盖到的？

### 问题等级

| 等级 | 定义 | 后果 |
|------|------|------|
| **重大** | 需求未满足、事实错误、方案不可行、数据损失、安全风险、兼容性破坏、不可恢复副作用、关键验证缺失 | 必须 `revise` |
| **重要** | 降低完整性/可靠性/可维护性，但不阻止交付 | 建议修复，不阻止交付 |
| **建议** | 表达、组织、风格、非必要优化 | 可采纳可不采纳 |

### 审查原则

1. **对抗而非确认** — 任务是找出为什么它是错的，不是为什么它可能对。
2. **证据驱动的疑问** — 每个质疑都有具体位置和实际证据。
3. **能具体指出错误的怀疑才是有效的审查** — 不能指出具体问题的"感觉不对"不是审查结论。
4. **不经手产物** — 审查者只写报告，不修改被审查的内容。

### 重大问题的报告格式

每个重大问题至少包含：**具体位置**（文件、行号）、**实际证据**（不是推测）、**影响**（为什么是重大的）、**最小修复方向**（只说方向，不替代实现）。

## 验证深度分级

根据任务风险选择验证深度（来自 UltraGoal 的 rigor 分层）：

| 级别 | 配置 | 适用场景 |
|------|------|---------|
| **vanilla** | 一次 fresh-context 验证器做最终签收 | 低风险改动，常规任务 |
| **standard** | 单验证器 + 对不确定项的中途重新检查 + 阈值附近的悲观双跑 | 中等风险，涉及多个文件 |
| **max** | 3-lens 验证面板（正确性/安全性/约束，三个盲判子 Agent 都必须 PASS） | 高风险，安全关键，数据迁移 |

## 跨模型审查（可选）

当任务风险足够高时，可以启用跨模型验证（来自 Humanize 的设计）：

- 默认情况下，同一模型 + fresh context 隔离已经足够
- 当单一模型可能产生系统性盲区时（如复杂安全逻辑、并发正确性），可要求审查者使用与生产者不同的模型系列
- 跨模型不是目的——**独立上下文比跨模型更重要**；跨模型是在独立上下文基础上的额外保险

## 不变式积累

完成并通过验证的任务产出，其关键验收条件可升级为**不变式（invariants）**（来自 UltraGoal）：

- 写入 `.agents/invariants/` 目录
- 后续所有验证的 L3 基线检查必须确认不变式未被破坏
- 不变式不是永久的——当需求变化时可以被显式更新或移除

## 降级处理

独立 Agent 不可用时，主 Agent 执行显式第二遍审查（重新阅读原始需求和实际产物，从审查者视角重新审视），并声明降级模式。Agent 输出异常时重试一次，之后主 Agent 接管。

## 交付

先说结论，再说过程：
1. 完成了什么，是否满足原始需求
2. 关键决定和产物位置
3. 验证方法与结果（含门控通过记录）
4. 未解决风险、假设和未覆盖范围

**验证失败时不得宣称完成。** 若失败与本次变更无关，给出相应证据。
