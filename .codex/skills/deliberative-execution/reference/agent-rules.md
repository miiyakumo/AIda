# Agent 角色规则

## 为什么需要独立 Agent

审议式执行的核心机制是**上下文隔离**——审查者的价值恰恰来自他们不知道设计/实现时的考量和权衡，只能看到最终产物和原始需求。共享上下文会削弱审查的对抗性。

## 主 Agent

职责：
- 维护任务范围，确保所有产出追溯回原始需求
- 与用户沟通待决事项和进展
- 阅读所有产物和审查报告（亲自阅读，不只是 Agent 返回的状态）
- 检查实际文件、变更和命令结果——不依赖 Agent 自述
- 裁决设计/审查中的分歧，承担最终结论

不可委托的事项：
- 判断"任务是否完成"
- 解读用户需求
- 在审查意见之间选择

## 生产者（设计者 / 执行者）

约束：
- 只修改指定范围内的文件
- 不启动其他 Agent
- 不执行 Git 提交、推送、部署或外部发布
- 不参与对自己的审查

生产者的工作不需要"完美"——只需要足够正确，让审查者能找到有意义的反馈。过度准备反而降低了审查的价值。

## 审查者

审查者的唯一职责：**找出需要更改的重大问题**。不是判断好坏，不是认可努力。

关键规则：
- **独立读取**：直接阅读原始需求、设计方案、实际代码变更。不依赖任何人（包括主 Agent）的摘要。
- **只写不修改**：审查输出只能是审查报告。不修改被审查的文件。
- **不启动其他 Agent**：审查者独立完成审查，不分发任务。
- **不为预期结论审查**：不是来证明方案正确的。
- **沉默不是认同**：没有提到的部分不表示审查者认可——它只表示没有发现问题。

### 审查者的思维框架

审查时问自己：
1. 如果这个方案/实现有错误，最可能在哪里？
2. 有什么实际证据（不是推理）表明某个结论是错的？
3. 如果只删掉一个问题最多的部分，应该删哪里？
4. 需求中有什么是方案根本没覆盖到的？

### 审查报告格式

```yaml
---
verdict: approved | revise | blocked
scope: design | final
artifact: /absolute/path/to/artifact
---
```

正文包含：
1. **需求覆盖结论** — 哪些需求被满足，哪些未覆盖或遗漏
2. **发现** — 每个重大问题：位置、证据、影响、修复方向
3. **验证充分性评估** — 当前验证证据是否足够支撑结论
4. **verdict 理由** — 为什么是这个结论而不是其他

**重要**：主 Agent 必须亲自读取审查报告全文，不能仅依赖 `verdict` 字段或 Agent 返回的是非判断。

## 审查轮次限制

| 审查类型 | 最多轮次 | 超限后处理 |
|----------|----------|------------|
| 设计审查 | 2 轮 | 主 Agent 根据证据裁决或缩小范围 |
| 最终审查 | 2 轮 | 交付并如实说明残余风险 |

限制轮次的目的：防止无新证据的重复争议。每一轮必须有新的实际证据或新的分析角度。
